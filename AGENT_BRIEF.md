# Agent brief

MOEX Sentinel разделяет торговый runtime между Core, Analytics и Worker.

Этот документ содержит постоянные границы и инварианты, а не текущий статус.
Основной агент всегда работает как root-оркестратор и поручает агентам любую
задачу разработки, включая исследование, документацию и ревью. Восемь профилей
из `.agents/`: архитектор, два senior, два профильных junior, универсальный
worker, независимый reviewer и security auditor.
Senior сначала согласует с root декомпозицию с файлами, владельцами, моделями
и приёмкой, затем выполняет сложную часть и поручает junior маленькие пакеты;
junior других агентов не создаёт. Простую задачу root может сразу дать junior.
Договорённости, лимиты и источники ролей — в
[описании оркестрации](docs/agent-orchestration.md) и `.agents/README.md`;
порядок работы — `local-development-coordinator`. Автор пакета не принимает его
единолично. Контекст, интеграцию и общую точку продолжения ведёт root по отчётам
исполнителей. Внутренний ACK root не требует нового разрешения пользователя
на уже авторизованные обратимые шаги.
Root отвечает за всю веху: описывает задачи, зависимости, порядок и владельцев, составляет брифы и делегирует по [правилам оркестрации](docs/agent-orchestration.md).
Новые Git-ветки, включая worktree с новой веткой, требуют отдельного явного
распоряжения пользователя; задача на исправление кода этого не разрешает.
Коммиты делает пользователь; агенты не выполняют stage, commit или push.
Предложения архитектора и senior, включая декомпозицию своего пакета, не снимают с root ответственность за план всей вехи.
Root сверяет фактические diff и доказательства с брифом, возвращает неполное автору и закрывает веху после приёмки обязательных задач и независимого review без неисправленных Critical/Important.
Root ведёт документацию и контекст приложения: инварианты — здесь и в тематических документах, очередь — в [плане](docs/phase-1-implementation-plan.md), краткий статус — в `develop/CURRENT.md`, история — в `develop/WORK_LOG.md`.
После значимых результатов, проверок, решений и блокировок и перед завершением сессии root обновляет материалы.
Секреты root не записывает; старые отчёты не выдаёт за подтверждение текущего runtime.
Точку продолжения брать из локального `develop/CURRENT.md`, если он есть;
для нового checkout использовать [шаблон CURRENT](develop/CURRENT.example.md).
Очередь — из
[актуального плана](docs/phase-1-implementation-plan.md). Подробности завершённых
этапов находятся в [пунктовом аудите](docs/milestone-audit.md).

Перед каждой вехой root проверяет актуальность постановки по текущему коду,
очереди, договорённостям, зависимостям и критериям приёмки; фиксирует результат
до декомпозиции/делегирования по [правилам оркестрации](docs/agent-orchestration.md).
V1: общая Python SERVICE_VERSION0.2.0 в shared contracts и независимая npm0.2.0.
Диагностика различает build frontend и наблюдённые runtime версии сервисов;
volatile Core version slot/TTL не заменяет durable recovery state Worker или O1
наблюдения торговли. [Контракт и приёмка](docs/superpowers/plans/v1-service-versions.md).

Решение владельца02.10: целевое размещение — одна PostgreSQL/одна database
для TEST и PROD, сервисы владеют своими таблицами. Отдельная PROD БД отменена.
Перенос Worker ещё не выбран; перечисленные ниже границы описывают текущий
код. SQLite хранит durable execution state, полный restore из broker API
не реализован. [Анализ оркестрации и восстановления](docs/audits/orchestration-and-worker-storage.md).

- Core — единственный владелец PostgreSQL и единственный источник подтверждённого состояния автоматов, циклов, лотов, решений, заявок, исполнений, аналитики и аудита.
- Worker — единственный владелец локальной SQLite. Он хранит восстановимое состояние исполнения и typed outbox, но не подключается к PostgreSQL.
- Analytics — отдельный процесс без credentials, портфеля и хранилища. Получает market-only batch от Core, рассчитывает показатели и возвращает Worker единый снимок с TTL.
- Portfolio snapshot worker — отдельный процесс внутри границы Core, который собирает сохранённую сводку торговли в PostgreSQL независимо от HTTP backend.

В HTTP-контуре Core синхронная операция с БД целиком выполняется в одном
потоке принадлежащего приложению пула (до четырёх незавершённых операций).
Session создаётся, используется и закрывается внутри этой операции; наружу
возвращаются DTO. Отмена ожидающего запроса не освобождает место до завершения
работы. При остановке приложение запрещает новые операции и дожидается уже
запущенных перед закрытием Engine. Async SDK, locks и runtime cache остаются
в event loop; контекст процесса копируется в поток. Вне HTTP сохраняется
прежнее выполнение сервисов, включая отдельный portfolio snapshot worker.
- Broker API — источник текущего портфеля, активных заявок, рыночных данных и результата исполнения.

При недоступности песочницы после первой попытки допускается максимум пять
повторов с паузами 1/3/5/7/9 секунд (`SANDBOX_RETRY_LIMIT` по умолчанию 5).
После исчерпания короткого бюджета transient failures Core gateway и Worker
продолжают recovery probes с паузой 60 секунд. Permanent failure блокирует
Core source до изменения конфигурации или перезапуска; заблокированному
permanent failure Worker нужен перезапуск runtime/процесса. Текущая policy:
`services/market_recovery.py`, `services/market_snapshot_gateway.py` в Core и
`runtime/analytics_broker.py` в Worker; историческая
[приёмка 0.9.5](docs/milestone-0.9.5-acceptance.md) не описывает позднейший cooldown.

В проекте одна цепочка миграций Core: `0001_baseline` → `0002_portfolio_snapshot_runs` → `0003_user_broker_archive` (текущий head кода), и один runtime-протокол. История из ранее использовавшихся хранилищ не импортируется. Миграция `0002` сохраняет торговые данные и требует пустой старой таблицы снимков портфеля; `0003` добавляет nullable `archived_at`, не удаляя строки или связи. Открытая позиция принимается через HOLD/BOOTSTRAPPING и становится IN_WORK только последним фактом одной атомарной группы.

Удаление broker settings архивирует запись (`archived_at`, `DISABLED`) и скрывает
её только из списка настроек. Исторический scope остаётся доступен внутренним
читателям; его account ID, уникальность и финансовые связи сохраняются.
Обычный `DISABLED` остаётся видимым и редактируемым. Старый PUT или disable не
возвращает архив; автоматическое восстановление/новая identity для того же
account scope запрещены. Откат `0003` при архивах прерывается под блокировкой
писателя; состояние и ревизия сохраняются. Уже выданные Worker credentials не
отзываются мгновенно: прекращение обычной работы происходит при очередной
проверке команд, как при прежнем disable.

Стратегия одна для всех позиций и определяется кодом. Analytics динамически
рассчитывает шаг усреднения и минимальный порог чистой прибыли по рынку каждого
инструмента. Общие настройки читаются из окружения Worker при старте; для
адаптивных порогов они служат fallback. Стратегия не хранится и не назначается
как отдельная сущность БД. Снимки стратегии и показатели в фактах — история
расчёта конкретного решения. Размер покупки задаётся общей настройкой,
резервы средств восстанавливаются из активных intent. Индивидуальных настроек
бюджета позиции нет; по решению пользователя веха 0.7 не добавляет новых полей
ресурсов. Настройки ресурсов и фактические адаптивные пороги — разные понятия.

Критические инварианты:

- кросс-ревью независимыми саб-агентами обязательно; критерии SOLID и чистоты кода находятся в [AGENTS.md](AGENTS.md);
- рыночный stream и история свечей принадлежат Core; Worker получает готовые
  показатели Analytics вместе со стаканом одного поколения, проверяет TTL по
  текущим часам и повторно перед отправкой заявки;

- каждое persisted-время нормализуется до UTC с точностью до миллисекунд;
- UUID события и `(automation_id, sequence_number)` дают устойчивую идентичность и порядок, поэтому глобальный auto-increment не нужен;
- bootstrap не создаёт брокерскую заявку или исполнение;
- при недостатке свободных средств решение — WAIT без нового intent;
- покупка запрашивает `STRATEGY_BUY_ORDER_LOTS`, по умолчанию один лот;
- покупка требует готового непрерывного окна SMA20 и подтверждённого разворота;
  полный take-profit учитывает обе комиссии, stop-loss сохраняет ценовой порог;
- исполнение, изменения цикла и outbox атомарны; запись наблюдения проверяет
  исходный цикл, чтобы устаревшее решение не создало intent после исполнения;
- metadata свечи остаётся в Worker; события заявки передают неизменяемый
  исходный `decision.strategy_snapshot` в Core;
- повторный запуск не дублирует автомат, цикл, лот или факт;
- постоянные `execution_price_repair_journal` в Core и Worker сохраняются;
  полное восстановление проекций должно после replay исходных событий применить
  завершённые коррекции, как описано в [runbook восстановления цены](develop/execution-price-repair.md);
- общая политика переходов различает команды пользователя и предложения Worker;
  CLOSED терминален, обычный HOLD возобновляется через команду Core;
- reconciliation, решение и отправка заявки связаны `process_id`; восстановление
  неопределённого intent использует отдельный стабильный процесс;
- удаление старых Docker volumes выполняется только после отдельного явного подтверждения.

Команды проверки приведены в [README](README.md), безопасное переключение — в [runbook](docs/clean-slate-cutover.md).
