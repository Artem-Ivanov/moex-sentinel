# Изолированная проверка торгового runtime

## Профиль Core PostgreSQL через настоящий HTTP

Из корня репозитория:

```bash
bash develop/scripts/profile_postgresql.sh --instruments 6 20 50 --warmup 3 --iterations 100 --batch-size 100 \
  > develop/reports/postgresql-profile.json
```

Нужны Docker и проектный `.venv` с dev-зависимостями. Runner создаёт собственный
контейнер `postgres:16-alpine` с динамическим loopback-портом и tmpfs, ждёт
готовности, передаёт URL только созданной БД, затем останавливает и удаляет
контейнер. При ошибке benchmark cleanup также выполняется, exit code сохраняется.
Рабочий Compose и persistent volumes не используются. `.env` не читается;
переданное извне значение `PG_PROFILE_DATABASE_URL` заменяется URL временной БД.

Модуль `develop.benchmarks.postgresql` использует настоящие Worker composition,
CoreClient и TCP HTTP endpoint production router. Core ingress, mapper и UoW
записывают данные в отдельную случайную схему PostgreSQL, созданную миграциями
Alembic head. После сценария удаляется только эта схема. Полное приложение Core
и его фоновые сервисы не запускаются. Analytics остаётся настоящим ASGI-приложением
в процессе; брокер и рынок синтетические.

JSON разделяет `initial_buy_filled` и `wait`. Начальный профиль включает реальные
для синтетического брокера BUY/FILLED и промежуточные WAIT при ограничении двумя
отправками на тик. Это не отдельная нагрузка SELL или конкурентный burst.
Три прогревочных такта исключены из измеряемого WAIT-профиля; 100 дальнейших
тактов обязаны дать по одному WAIT/NO_THRESHOLD на инструмент без новых заявок.

| Метрика | Что измеряется |
| --- | --- |
| `decision_tick_ms` | Analytics, подготовка/решения Worker, сохранение и ожидание tracking. |
| `queue_wait_ms` | От добавления ORM-строки outbox до первой попытки CoreClient; включает оставшееся ожидание commit Worker. |
| `http_roundtrip_ms` | Полный CoreClient.publish_facts: сериализация, TCP, router/ingress, ответ и проверка клиентом. |
| `core_ingress_ms` | Весь TradingFactIngressService.publish с транзакциями групп автоматов. |
| `sql_execution_ms` | Отдельный cursor.execute внутри ingress; без seed/migrations, диагностических COUNT и pool pre-ping. |
| `session_commit_including_flush_ms` | Session.commit, включая возможный flush. |
| `dbapi_commit_ms` | Фактический вызов PostgreSQL DBAPI COMMIT. |
| `outbox_drain_ms` | Полное опустошение очереди, включая проверочные COUNT между batch. |

Часы длительностей — `perf_counter`, а не логические минутные часы рынка.
Каждое распределение содержит размер выборки, min/max, p50 (медиана), p95/p99
(nearest rank). Дополнительно публикуются SQL/commit/fact counts на HTTP-запрос,
суммы длительностей и throughput с явно указанной областью измерения.
HTTP включает ingress, ingress включает SQL и commit: эти величины нельзя
складывать как независимые и нельзя вычитать их p95 для получения p95 сети.
Ожидание очереди измерено на факт, остальные выборки — на свой этап; суммы времени
ожидания отдельных фактов также не являются временем всей последовательной цепочки.

После замеров проверяется потеря HTTP-ответа **после успешного Core commit**:
ASGI-обёртка обрывает тело ответа, настоящий клиент получает ошибку транспорта.
Worker закрывается и открывает ту же SQLite; сравниваются сохранённые envelopes,
точный replay и итоговые Core-факты. Проверяются пустая очередь и неизменные
счётчики Core orders/входов в SDK. Счётчик SDK увеличивается до синтетических
assertions, поэтому перехваченное исключение не скрывает повторную отправку.

Это последовательный producer → drain, один HTTP worker и один источник рынка.
PostgreSQL работает на tmpfs: `dbapi_commit_ms` не характеризует fsync/IOPS
постоянного production-диска. Прогон не доказывает production SLA, предел
конкурентной нагрузки или необходимость переноса Worker SQLite. Версия PostgreSQL
и тип хранения указаны в JSON; целевой порог нагрузки пока не задан.

Тесты профилировщика на **отдельной тестовой** PostgreSQL:

```bash
POSTGRES_TEST_DATABASE_URL='postgresql+psycopg://sentinel_test@127.0.0.1:55439/sentinel_test' \
  .venv/bin/pytest -q develop/tests/test_postgresql_benchmark.py
.venv/bin/pytest -q develop/tests/test_postgresql_profile_runner.py
```

Для тестов используется только URL отдельно поднятой тестовой БД, никогда URL
рабочего Core. При отсутствии переменной PostgreSQL-тесты явно пропускаются.

## Предыдущий профиль SQLite

Из корня репозитория с установленными dev-зависимостями:

```bash
.venv/bin/python -m develop.benchmarks.runtime --instruments 6 20 50 --warmup 3 --iterations 100
.venv/bin/pytest -q develop/tests/test_runtime_benchmark.py
```

Результат — JSON в stdout. Ненулевой exit code означает нарушение проверяемого
инварианта или ошибку запуска. Задержки сами по себе не считаются ошибкой: SLA
пока не задан. Для p95/p99 используется nearest rank, для p50 — медиана.

Проверяется настоящий Analytics endpoint через HTTPX ASGI transport, настоящий
Worker composition, планировщик, динамическая стратегия, сохранение решений,
файловая SQLite и FactSynchronizationService. Факты принимает настоящий Core
ingress/repository на второй временной SQLite. Рыночные данные и брокер полностью
синтетические. Конфигурация окружения и рабочие БД не читаются. TemporaryDirectory
удаляет обе БД после каждого сценария; код не принимает URL базы или брокера.

Перед замерами для каждого инструмента проходит BUY → FILLED. Настоящий rate
limiter ограничивает отправку двумя заявками за тик; эти начальные тики и warmup
исключены из статистики. Затем рынок постоянен: измеряется обработка WAIT для
открытых позиций. Один брокер, один аккаунт, 20 полных свечей на инструмент.
Идентичные генерации свечей заново привязываются к каждому логическому моменту.

`tick_ms` включает получение Analytics, решения, сохранение и ожидание завершения
tracking. `delivery_ms` отдельно измеряет полное опустошение outbox через Core.
`decisions_per_second` относится только к сумме времени тиков;
`pipeline_decisions_per_second` включает доставку. Подготовка следующей генерации
и подсчет очереди между тиком и доставкой не входят в замеры. `delivery_ms`
включает SQL-count, которыми проверяется прогресс между batch. Показан размер очереди после
тика перед доставкой. Это последовательный producer → drain, не независимые
процессы с конкурентной доставкой.

В каждом сценарии дополнительно теряется ответ Core после успешного commit:
Worker сохраняет retry, выполняет еще один тик без доставки, затем закрывается
и заново открывает SQLite/runtime. Пока у автомата есть неподтвержденные факты,
PositionStateHydrationService блокирует подготовку новых решений: поэтому очередь
в этом сценарии не обязана расти на каждом тике. Проверяется сохранение имеющейся
очереди и восстановление после подтверждения. Сверяются размер очереди после перезапуска,
неизменность повторно отправленных envelope, прием replay, полное опустошение
очереди, количество решений в Worker/Core и отсутствие новых broker dispatch
после восстановления. Перезапуск управляемый; убийство процесса во время SQLite
commit и восстановление незавершенного брокерского ордера здесь не моделируются.

Логические часы переходят на минуту за тик, а длительности измеряются
`perf_counter`. Поэтому этот тест не проверяет TTL при реальном ожидании, реальную
частоту заявок, сетевые задержки, SDK/стакан, PostgreSQL, контейнерные лимиты или
заявочный burst. Результат характеризует данный профиль на машине запуска и
не является пределом торговой производительности или подтверждением SLA.
