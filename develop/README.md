# Вспомогательные материалы разработки

Здесь размещаются одноразовые скрипты, диагностические инструменты и прототипы,
которые не входят в приложение. Каталог исключён из Docker-контекста и
Python-дистрибутива; runtime не должен импортировать отсюда код.

- `scripts/` — миграция схемы и наполнение sandbox через штатный API.
- `tests/` — проверки вспомогательных скриптов; запускаются отдельно.
- `benchmarks/` — изолированные измерения Analytics/Worker/Core с имитацией брокера.
- `reports/` — агрегированные результаты проверок и снимки синтетического UI.
- `legacy-bytecode/` — локальный архив кэша удалённых Python-модулей с сохранением
  путей относительно корня проекта. Файлы `.pyc` игнорируются Git. Архив может
  отсутствовать в новом checkout и не требуется для работы или тестов.

В архиве сохранены остатки прежнего `moex-migrate-reference-data`. Его исходники
и регистрация CLI были удалены при переходе на текущую схему. Это был перенос
данных из существующих таблиц в той же БД, а не генератор подключений. Архив
не содержит восстановленного рабочего CLI и не предназначен для запуска;
для переноса подключений нужен источник прежней базы и проверка совместимости
со схемой назначения.

Исходный контракт описан в
[историческом плане миграции](../docs/superpowers/plans/2026-08-10-user-broker-reference-migration.md).

## Подготовка пустой базы

Из корня проекта, после запуска Compose и установки `uv sync --all-extras`:

```bash
bash develop/scripts/migrate_schema.sh
.venv/bin/python -m develop.scripts.seed_sandbox
```

Первая команда применяет актуальную схему через Compose-сервис `migrations`.
Вторая выполняет dry-run: проверяет локальный API и конфигурацию, ничего не
создаёт и не требует токена. Поддерживается только локальный API и адаптер
T-Invest Sandbox. Историческая база для этого процесса не нужна.

Для наполнения нужен действующий sandbox-токен из переменной
`TINVEST_SANDBOX_TOKEN` либо отдельного локального файла с самим токеном.
Значение не передаётся аргументом команды и не выводится скриптом:

```bash
.venv/bin/python -m develop.scripts.seed_sandbox --apply
```

Путь к уже существующему файлу можно передать через `--token-file`; имя другой
переменной — через `--token-env`. При нескольких счетах укажите `--account-id`.
Скрипт переиспользует подключение с тем же `--display-name`, проверяет доступность,
выбирает счёт и синхронизирует каталог. Неоднозначный выбор счёта требует явного
параметра. Повторный запуск не создаёт дубликат подключения.

Подключение без выбранного счёта считается незавершённой настройкой и может
быть дополнено при повторном запуске. Публичный API не различает отключённый
черновик и обычный черновик без счёта. Отключённое подключение с уже выбранным
счётом скрипт не включает. Изменившийся токен обновляется до проверки подключения.

Синхронизация принимает существующие позиции брокера. Для пустого портфеля
автомат создаётся только при явном `--instrument-id` (параметр повторяемый).
Используйте внутреннее поле `id` инструмента из локального каталога,
а не тикер или внешний идентификатор брокера. Скрипт вызывает штатный `/trade`
и переиспользует уже существующий активный автомат.

Состояние `IN_QUEUE` означает, что автомат создан и ждёт Worker. Оно не доказывает
совершение сделки. Для входа нужны работающий Worker с `STRATEGY_ENABLED=true`,
доступная торговая сессия, рыночные данные, средства на sandbox-счёте и сигнал
стратегии. Скрипт не записывает вымышленные позиции, исполнения или аудит в БД
и не открывает или пополняет внешний sandbox-счёт.

Проверки скриптов:

```bash
.venv/bin/python -m pytest develop/tests -q
```

Для новых инструментов документируйте команду запуска, входные данные и
изменяемые ресурсы. Секреты и дампы с данными не добавляйте в репозиторий.

## Проверка Analytics и продвижения Worker

Результаты проверки SDK, VPN и stream RPC, включая независимый HTTP/2-клиент:
[расследование Sandbox stream](market-stream-investigation-2026-09-09.md).

`check_analytics_runtime.py` читает конфигурацию активных автоматов из SQLite
Worker в режиме `mode=ro` и запрашивает штатный Analytics. Не отправляет заявки
или факты и не изменяет хранилища. Запуск из корня репозитория:

```bash
docker compose -f compose.yml exec -T trading-automaton python - \
  --attempts 4 --interval 1 --require-all-fresh \
  < develop/scripts/check_analytics_runtime.py
```

Вывод содержит только счётчики, свежесть, задержки и время последнего решения.
Код выхода `0` подтверждает прохождение проверки свежести всеми инструментами
в последней попытке и согласованность повторных снимков; `1` означает, что
проверка не пройдена; `2` — техническую ошибку. Продвижение торгового цикла
проверяется отдельно по `trade_decision_count_delta` и
`last_trade_decision_advanced`: сам ответ Analytics не доказывает новое решение.

## Измерения производительности и очереди

[Benchmark](benchmarks/README.md) создаёт временные SQLite, имитирует брокера и
не обращается к рабочим базам. Для воспроизведения принятого профиля:

```bash
.venv/bin/python -m develop.benchmarks.runtime --instruments 6 20 50 --warmup 3 --iterations 100
docker compose -f compose.yml exec -T trading-automaton python - \
  --samples 120 --interval 5 < develop/scripts/observe_worker_progress.py
```

Вторая команда только читает агрегаты Worker: прогресс решений, размер очереди,
возраст старейшей PENDING и максимальный retry_count сохранённых строк.
Подтверждённые строки удаляются; этот счётчик не равен общему числу HTTP-повторов.

Browser smoke запускается после `npm run build` в `frontend` командой
`node develop/scripts/check_brokers_ui.mjs`. Требуется установленный Playwright
и Chrome; `PLAYWRIGHT_MODULE` может указывать путь к существующему `index.mjs`.
Флаг `--runtime` добавляет GET-only проверку localhost:8080. Изменения формы
выполняются только с имитацией API; screenshots содержат синтетические данные.

## Восстановление очереди после утечки `decision_candle_at`

`repair_decision_candle_facts.py` предназначен только для случая, когда приватный
ключ `decision_candle_at` попал в `BROKER_ORDER_STATE_CHANGED.strategy_snapshot`.
Нужны исправленный образ Worker и штатно остановленный сервис
`trading-automaton`; все записи `worker_runs.clean_shutdown` должны быть истинны.
Core должен оставаться доступным. Worker не запускайте до окончания восстановления.

Проверка без записи в SQLite и публикации фактов (из корня репозитория):

```bash
docker compose run --rm --no-deps -T --entrypoint python trading-automaton - --database /app/data/trading_automaton.db --core-url http://backend:8000 < develop/scripts/repair_decision_candle_facts.py
```

Для применения повторите эту команду, добавив `--apply` перед перенаправлением
`<`. Параметр `--max-facts` ограничивает суммарную очередь затронутых автоматов
(по умолчанию 10000). Локальный запуск поддерживает те же аргументы:
`.venv/bin/python -m develop.scripts.repair_decision_candle_facts --help`.

Скрипт сверяет исправляемый snapshot с решением в `trade_decisions`, проверяет
непрерывность очереди, ревизии и последовательности Core, отказывает при фактах
изменения состояния автомата. Он удаляет только приватный ключ из ещё не принятых
фактов, возвращает затронутые FAILED в PENDING, публикует неизменённые UUID и
последовательности через `CoreClient`, удаляет подтверждённые факты из outbox и
сверяет кэш с актуальным состоянием Core, включая HOLD/CLOSED и resume_requested.
Брокерские заявки и команды возобновления работы не отправляются.

Вывод содержит только агрегированные счётчики или фиксированный код/тип ошибки.
При прерывании повторите ту же команду с `--apply`: временная таблица
`decision_candle_fact_repair` хранит только ID автоматов и границы очередей.
Она позволяет повторить публикацию после потери ACK и удаляется после полного
успеха; вручную удалять её при незавершённом восстановлении нельзя.
