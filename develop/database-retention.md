# Месячная очистка БД

`scripts/cleanup_database.py` обслуживает существующее хранилище Core или Worker.
Скрипт не входит в образ приложения; его можно передать на stdin Python
владеющего БД контейнера. Никакого расписания и автоматического запуска нет.

Без `--apply` выполняется только отчёт. Граница — текущее время UTC минус один
календарный месяц, с сохранением времени суток. Для 31 марта граница — 28 февраля
(29 в високосном году). Удаляются записи **строго старше** границы.

| Хранилище / таблица | Правило удаления |
|---|---|
| Core `trade_audit_events` | Старые некритичные диагностические события; сохраняются события автоматов с незавершёнными заявками или неопределёнными резервами |
| Worker `business_audit_events` | Старые некритичные события; сохраняются события автоматов с активными/незавершёнными intents или недоставленными фактами |
| Core `portfolio_snapshots` | Старые снимки, кроме последних для каждого брокерского подключения, счёта и валюты |
| Core `position_valuation_snapshots` | Старые оценки, кроме последних для каждого подключения и цикла позиции |

При нескольких снимках с одинаковым последним временем сохраняются все такие
строки. Критичные события сохраняются независимо от возраста. Отчёт перечисляет
23 бизнес-таблицы Core или 10 таблиц Worker; для сохраняемых таблиц указывается
причина. Служебная `alembic_version` и неизвестные таблицы не изменяются.

`automation_events` содержит принятые envelopes и дедупликацию последовательности.
Это финансовые факты, их нельзя считать обычными логами. Заявки, исполнения,
решения, лоты и распределения сохраняются вместе с историей. Ключи повторов
`broker_intents` и `trading_submit_reservations` сохраняются бессрочно; `fact_outbox`
удаляется штатным ACK. Конфигурация, состояние автоматов/циклов, комиссии,
владельцы Worker, baseline, сверки допуска и аудит изменения допуска сохраняются.
Старые `portfolio_snapshot_runs` остаются якорями дедупликации сбора.

## Запуск

Из корня проекта, с настроенным `DATABASE_URL` или `AUTOMATON_DATABASE_URL`:

```bash
python develop/scripts/cleanup_database.py --store core
python develop/scripts/cleanup_database.py --store worker
```

Для существующих PROD контейнеров с их собственными переменными окружения:

```bash
sudo docker exec -i moex-sentinel-prod-backend-1 python - --store core \
  < develop/scripts/cleanup_database.py
sudo docker exec -i moex-sentinel-prod-trading-automaton-1 python - --store worker \
  < develop/scripts/cleanup_database.py
```

Проверив отчёт, для удаления добавить `--apply` в соответствующую команду.
Параметр `--batch-size` ограничивает число строк одной транзакции, по умолчанию
1000. Условия сохранения проверяются заново для каждой партии. При ошибке текущая
партия откатывается; уже завершённые партии остаются удалёнными. Следующий запуск
повторно вычисляет подходящие строки. `would_delete` показывает число подходящих строк перед началом операции,
`deleted` — число фактически удалённых. При параллельной записи эти значения
могут различаться. PostgreSQL пропускает строки, заблокированные другой
транзакцией; последующий отчёт покажет оставшиеся кандидаты.

Отчёт содержит агрегаты, без payload,
идентификаторов счёта, паролей и URL подключения.

Core использует PostgreSQL, Worker — существующий SQLite файл. Отсутствующая или
несовместимая БД не создаётся и не мигрируется скриптом. В режиме отчёта используются
транзакции только для чтения. Скрипт не обращается к брокеру, не отправляет заявки,
не меняет торговый допуск и не выполняет backup, restore или VACUUM.

DELETE освобождает место внутри БД для повторного использования. Размер файлов
на диске после него может остаться прежним; принудительное уменьшение файлов
не входит в эту процедуру.

## Проверка

```bash
PYTHONPATH=src python -m pytest \
  develop/tests/test_cleanup_database_core.py \
  develop/tests/test_cleanup_database_worker.py -q
```

Core-тестам нужен `POSTGRES_TEST_DATABASE_URL` отдельного тестового PostgreSQL;
они создают и удаляют собственную схему. Worker-тесты используют временные SQLite
файлы. На рабочей БД эти тесты не запускаются.
