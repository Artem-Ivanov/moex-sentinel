# Sandbox MarketDataStream: результаты расследования

Статус после проверки 12:04 UTC: рыночный поток снова передаёт данные, Worker создаёт
новые решения. Причина прежнего отказа и последующего восстановления не установлена.
Веха 0.5 принята по DoD с явным ограничением непостоянной свежести стаканов;
непрерывная доступность всех шести инструментов не подтверждена.
Документ можно использовать как
основу обращения в поддержку; внешних сообщений из этой сессии не отправлялось.

## Восстановление и контрольная проверка

Около 12:01 UTC повторная независимая HTTP/2-проба с теми же настройками дала:

| Контроль | HTTP status | gRPC status | Результат |
| --- | --- | --- | --- |
| MarketDataStream, открытая отправка | 200 | Не получен до конца наблюдения | 62 DATA chunks за 15 секунд |
| MarketDataStream, отправка завершена | 200 | 0 | Штатное завершение |
| Unary GetOrderBook | 200 | 0 | Получен ответ |
| Заведомо отсутствующий метод | 200 | 14 | UNAVAILABLE |

DATA chunks — части HTTP/2-ответа, а не число котировок. Локальный таймаут
завершил наблюдение открытого потока; это не отказ сервера. Ответ 14 на
отсутствующий метод нельзя считать эталоном METHOD_NOT_FOUND или доказательством
ошибки маршрутизации. SDK, endpoint и credentials при этих проверках не менялись.

Проверка Core → Analytics → Worker в 12:01:42–12:01:49 UTC:
шесть из восьми замеров приняли все шесть инструментов, включая последний;
два замера отклонили один устаревший инструмент. Решения Worker: +17,
код завершения проверки 0. К 12:03:17 UTC очередь фактов опустела.

Расширенная проверка в 12:03:17–12:03:47 UTC выявила ограничение:
из 30 замеров только пять приняли все шесть инструментов, остальные приняли
от двух до пяти. UNAVAILABLE не было; максимальный возраст стакана — 7092 мс.
В последнем замере один стакан старше TTL (2038 мс при лимите 2000 мс),
поэтому `--require-all-fresh` завершился с кодом 1. Это не успешная приёмка
стабильной свежести. При этом Worker создал ещё 65 решений, история содержала
104–120 свечей, максимальная задержка HTTP составила 152 мс. Одна проверка
повторного snapshot ID не обнаружила изменения содержимого. За это окно очередь
фактов изменилась с пустой до 54 PENDING; само это изменение не доказывает сбой
доставки при продолжающемся создании фактов.

Независимый контроль outbox в 12:04:05–12:04:15 UTC подтвердил доставку
исходных 12 фактов за пять секунд; `retry_count=0` во всех трёх замерах
не исключает повторных HTTP-попыток внутри вызова доставки. Возраст текущей очереди
в этих замерах не превышал 1,649 секунды; за окно создано ещё 24 решения.
Ревью закрытия по DoD: analytics_boundary_audit, APPROVED с указанным
ограничением свежести. Подробности — в
[приёмке 0.5](../docs/milestone-0.5-acceptance-2026-09-09.md).

Reflection v1 и v1alpha на запрос единственного символа
MarketDataStreamService вернули UNIMPLEMENTED. Описание не получено:
это не доказывает отсутствие рыночного сервиса. Временный пакет reflection
1.76.0 установлен отдельно в `/tmp`, зависимости проекта не изменены.

## Возраст стаканов и интервалы обновлений

Один дополнительный 20-секундный замер через отдельное SDK-соединение принял
все шесть подписок и получил 400 стаканов (28–130 на инструмент).
Возраст 394 последующих сообщений при получении: p50 — 47,86 мс,
p95 — 157 мс, максимум — 347,26 мс; сообщений старше двух секунд нет.
Начальные шесть стаканов не старше 44,35 мс.

При этом максимальный интервал между сообщениями одного инструмента —
5636,38 мс; семь интервалов превысили две секунды. Интервалы между биржевыми
временами формирования также превышали две секунды семь раз, максимум —
5417,85 мс. Неконсистентных или переставленных сообщений не было.
В 16 последовательных обновлениях содержимое уровней совпало, поэтому
строгое утверждение «поток передаёт только изменения уровней» не подтверждено.

Это свидетельствует о длинных паузах между обновлениями на проверенном
соединении при небольшом возрасте приходящих данных. Постоянного отставания
доставки в этой пробе не наблюдалось. Она не измеряет существующее соединение
Core напрямую и не исключает задержек на нём. У 18 сообщений возраст немного
отрицательный (минимум −6,78 мс): разница часов или точность измерения также
влияют на эту метрику, её нельзя считать чистой сетевой задержкой.

Read-only обзор кода подтвердил сохранение биржевого `OrderBook.time`
в source и gateway; время чтения snapshot не продлевает свежесть.
Документация определяет [время формирования стакана](https://developer.tbank.ru/invest/services/quotes/marketdata)
и [минимальный интервал отправки](https://developer.tbank.ru/invest/intro/developer/speedup),
но не гарантирует новое сообщение каждого инструмента раз в две секунды.
Изменять TTL или искусственно обновлять timestamp оснований нет.

## Исторический отказ до восстановления

Независимый клиент Node.js HTTP/2, без Python SDK и grpcio, получил:

| Режим отправки | HTTP status | gRPC status | Категория сообщения | RST | Задержка |
| --- | --- | --- | --- | --- | --- |
| Поток запросов открыт | 200 | 12 | METHOD_NOT_FOUND | 8 | 92 мс |
| Отправка завершена | 200 | 12 | METHOD_NOT_FOUND | 0 | 83 мс |

Данных рынка в ответе не было. TLS-проверка сертификата и имени хоста включена;
использован публичный CA, поставляемый SDK. Авторизация передавалась только
настроенному сервису, её значения в диагностический вывод не включались.

Таким образом, в открытом потоке перед сбросом приходит статус
`UNIMPLEMENTED / METHOD_NOT_FOUND`. Python gRPC-клиент сообщает последующий
`CANCELLED / RST_STREAM 8`, из-за чего первоначальная диагностика описывала
только сброс. Причина, по которой сервер или маршрутизатор не находит метод,
из доступных клиентских данных не установлена.

## Адрес, контракт и версия

- Настроенный адрес: `sandbox-invest-public-api.tbank.ru:443`.
- RPC: `/tinkoff.public.invest.api.contract.v1.MarketDataStreamService/MarketDataStream`.
- Установлен `t-tech-investments==1.49.3`. Официальный пакетный реестр
  2026-09-09 подтвердил `INSTALLED = LATEST = 1.49.3`.
- Старый и новый Python API используют одинаковые stub, URI, фабрику каналов
  и авторизационные метаданные. Более новой версии в официальном реестре
  на дату проверки нет.
- RPC соответствует [опубликованному контракту](https://developer.tbank.ru/invest/api/market-data-stream-service-market-data-stream).
  [Сравнение контуров](https://developer.tbank.ru/invest/intro/developer/sandbox/url_difference)
  отмечает доступность сервиса котировок в Sandbox. Это не объясняет наблюдавшийся
  ответ METHOD_NOT_FOUND и не позволяет утверждать, что все Sandbox-потоки
  в принципе не поддерживаются.

## Дополнительные проверки

- Прямые вызовы stub без Core gateway, менеджера подписок и прикладных
  преобразований воспроизводят отказ.
- Синхронный и асинхронный Python-клиенты дают одинаковый результат:
  открытая отправка — RST8, завершённая — METHOD_NOT_FOUND.
- На хосте и в Docker результат одинаков. SDK и protobuf совпадают;
  grpcio на хосте 1.83.0, в контейнерах 1.83.1. Node воспроизводит отказ
  без обеих версий grpcio.
- Пользователь отключил VPN, Core перезапущен; симптом сохранился.
  Это не доказывает, что VPN никак не влиял на предшествующие ошибки.
- Явных proxy-переменных окружения не обнаружено; системный сетевой путь
  только этим фактом не определяется.
- Unary-загрузка истории и GetUserTariff успешны. GetUserTariff показал
  MarketDataStream open=0 при limit=32. Нагрузка подписок — 12 стаканов/свечей
  при лимите 300. Документированная задержка счётчика соединений — до двух
  минут; общий трафик других приложений с внешнего IP не измерен.
- Во время исторического отказа Worker не получал свежие данные и не создавал
  новых решений. Доставка фактов продолжала работать. Ограничение TTL не ослаблялось.

## Воспроизведение

Из корня проекта с существующей локальной конфигурацией:

```sh
python3 -m pip index versions t-tech-investments \
  --index-url https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple
.venv/bin/python -m develop.scripts.check_market_host_transport
.venv/bin/python -m develop.scripts.check_market_http2
.venv/bin/python -m develop.scripts.check_market_http2 --controls
.venv/bin/python -m develop.scripts.check_market_reflection
.venv/bin/python -m develop.scripts.check_market_event_timing
```

Скрипты читают локальные настройки и существующее Sandbox-подключение,
не создают торговых заявок и не изменяют БД. Каждый HTTP/2-запрос ограничен
15 секундами, процесс Node — 20 секундами. Reflection требует временного пакета;
инструкция установки находится в docstring скрипта. Python-сравнение также ограничивает
каждый RPC 15 секундами. Это не общий deadline чтения конфигурации из БД.

Проверка действующего Worker:

```sh
docker compose -f compose.yml exec -T trading-automaton python - \
  --attempts 4 --interval 1 --require-all-fresh \
  < develop/scripts/check_analytics_runtime.py
```
