# Восстановление единиц цены исполнения

`develop/scripts/repair_execution_prices.py` исправляет подтверждённый случай,
когда полная стоимость исполненной заявки была сохранена как цена одной бумаги.
Инструмент не обращается к брокеру, не создаёт заявки и не изменяет количество
исполненных лотов, стоимость исполнения, комиссии, идентификаторы или sequence.

По умолчанию выполняется dry-run. Worker должен быть штатно остановлен,
`worker_runs.clean_shutdown` должен подтверждать остановку, outbox — быть пустым,
а незавершённые и неопределённые intents — отсутствовать. Операционное применение
выполняется только после проверки dry-run и независимого ревью.

```sh
python develop/scripts/repair_execution_prices.py \
  --worker-database /repair/trading_automaton.db \
  --core-database-url-env DATABASE_URL
```

`DATABASE_URL` уже должен быть передан процессу штатным окружением Core.
Его значение не следует включать в аргументы, отчёты или вывод терминала.
Для применения к той же паре баз добавляется `--apply`. Параметр `--max-rows`
ограничивает число строк каждой выбранной таблицы; значение по умолчанию — 10000.
Вывод CLI содержит только режим, количества изменений либо фиксированный код
отказа. Dry-run открывает SQLite через URI `mode=ro` и не создаёт journal.
Для SQLite в режиме WAL каталог может требовать доступной служебной SHM-памяти:
доступность каталога и запрет записи в саму базу — отдельные свойства.

## Граница доказанного исправления

Кандидат должен одновременно удовлетворять условиям:

- `executed_price == executed_amount > 0`;
- `executed_lots * lot_size > 1`;
- нормализованная цена `executed_amount / (executed_lots * lot_size)` удовлетворяет
  стороне лимитной заявки и отличается от её лимита не более чем на 20%.

Правильное равенство `unit_price * executed_lots * lot_size == executed_amount`
означает отсутствие ошибки. Необъяснимые расхождения блокируют весь план;
частичный ремонт сомнительных групп не выполняется.

План воспроизводит bootstrap и исполнения в порядке принятых Core событий,
проверяет существующую LIFO-топологию и остатки лотов. Core и Worker должны
совпадать по scope, связям, количествам, суммам и комиссиям. Для истории читаются
только события исполнения и bootstrap-открытия лота; решения и аудит не расходуют
лимит графа. Повторная проверка контролирует как значения строк, так и точный
набор идентификаторов.

Пересчитываются цена исполнения, цены входа/выхода лотов, распределённые стоимости,
реализованный P&L и текущие агрегаты циклов. Net использует общую с Worker формулу:
net realized + gross unrealized − оплаченная комиссия входа оставшихся лотов.
Комиссии закрытых частей уже входят в realized и повторно не вычитаются.
Промежуточные доли комиссии не округляются; округление выполняется на границе
сохранённых денежных полей с точностью 9 знаков.

Текущая рыночная оценка сохраняется: для ненулевого остатка исходный mark
однозначно выводится из `(unrealized_pnl + invested_amount) / units`. Исправляется
себестоимость, но не цена и время рыночного наблюдения. Mark должен быть
положительным, конечным и находиться в пределах 20% последнего лимита исполнения;
это исключает сохранение ошибочного total в качестве текущей рыночной цены.
При большем движении цены или неоднозначной оценке инструмент отказывает.

## Постоянные журналы корректировок

Операционное восстановление добавляет **в обе базы** maintenance-таблицу
`execution_price_repair_journal`. Это отдельное изменение схемы восстановления,
выполняемое вне Alembic; оно не добавляет зависимость Analytics от хранилищ.

| Поле | Назначение |
| --- | --- |
| `plan_id VARCHAR(64) PRIMARY KEY` | SHA-256 канонического плана |
| `status VARCHAR(16)` | `PREPARED` либо `COMPLETE` |
| `plan JSON` | Версия, необходимые before/after-поля, IDs и контрольные хэши/наборы графа |
| `created_at VARCHAR(64)` | UTC-время создания записи |

Порядок применения:

1. Сохранить `PREPARED` в Worker, повторно получить SQLite write lock и проверить
   остановку, пустой outbox и исходный граф.
2. В одной Core-транзакции изменить проекции и сохранить `COMPLETE` с тем же планом.
3. В одной Worker-транзакции изменить локальные проекции и отметить `COMPLETE`.

После сбоя между шагами 2 и 3 Worker остаётся остановленным. Повторный запуск
с теми же базами находит `PREPARED`, проверяет checksum, неизменяемые части графа
и допускает только точные before/after-состояния плана. Неизвестное изменение
прерывает восстановление. Завершённый повтор не создаёт новых коррекций.

Журналы **сохраняются после ремонта**. Принятые `automation_events` и исторические
решения/аудит не переписываются: они остаются свидетельством первоначальной
обработки и основанием точного replay принятых envelopes. Любое будущее полное
восстановление Core-проекций из этих событий обязано после базового replay применить
Core-коррекции завершённых журналов в порядке их создания. Иначе неверная цена
вернётся. Этот скрипт восстанавливает согласованную пару текущих хранилищ и не
заменяет процедуру полного projection rebuild.

## Проверки

Синтетические тесты находятся в `develop/tests/test_repair_execution_prices.py`.
Проверка реальных типов и ограничений Core выполняется в
`develop/tests/test_repair_execution_prices_postgresql.py`: существующий fixture
создаёт отдельную случайную PostgreSQL-схему, применяет миграции, проверяет
коррекцию и восстановление после потерянного подтверждения Core, затем удаляет
только эту тестовую схему. Рабочая схема в этом тесте не используется.
