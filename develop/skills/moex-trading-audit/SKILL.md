# Аудит торговли MOEX Sentinel

Проверь фактическую торговлю по последовательности пользователя. Результат — сопоставление по каждой позиции, доказанные причины аномалий и задачи на исправление либо подтверждение ожидаемой работы в указанном интервале. Отвечай по-русски.

Для офлайн-аудита используй только предоставленные материалы, если так ограничил пользователь; отсутствие доступа к коду или runtime явно укажи. Если запись файлов запрещена, выдай отчёт и задачи в ответе.

## Границы и исходные данные

- Найди корень проекта и прочитай его `AGENTS.md`, `docs/trading-strategy.md`, текущую реализацию стратегии. Источники и команды: [references/runtime-sources.md](references/runtime-sources.md).
- Аудит сам по себе не разрешает отправлять заявки, создавать/возобновлять/закрывать автоматы, синхронизировать каталог, менять ключи, настройки, БД или перезапускать сервисы. Используй read-only API, журналы и read-only транзакции. Эксперименты и воспроизведение — на копии/отдельной тестовой БД. Рабочие volumes сохраняй.
- Фиксируй UTC-интервал, broker/account/instrument/automation ID, версию образа, время каждого запроса. Работающий сервис меняется между запросами: не выдавай последовательные чтения за атомарный снимок.
- Сохраняй материалы в `develop/reports/<audit-id>/`. Не выгружай credentials: публичный `GET /api/brokers` в этой версии возвращает `fields` с ключом. Нужные идентификаторы извлекай в памяти; конфигурацию выводи по allowlist. В переиспользуемый skill не копируй ключи, значения портфеля и ID конкретного сеанса.

## Порядок проверки

### 1. Прочитать открытые позиции

Прочитай брокерские позиции и список автоматов. Соедини данные по broker/account и внешнему instrument ID через внутренний ID каталога. Тикер служит подписью, не уникальным ключом.

Проверь единицы quantity по адаптеру/схеме. В текущем `/api/positions` quantity уже выражено в лотах; shares = lots × lot_size. Отдельно выдели денежные строки портфеля (например, RUB000UTSTOM): отсутствие торгового автомата у денег не является потерей позиции.

Для каждого инструмента сопоставь брокерское количество, Core-количество/состояние, локальные лоты и cache Worker. Установи происхождение лотов: bootstrap, reconciliation или исполнение заявки. `POSITION_CONSISTENT` для Worker не доказывает согласованность Core.

### 2. Получить котировки и определить ожидаемую ветку

Запиши best_bid, best_ask, last_price, lot_size, tick_size, валюту, торговый статус, разрешение limit/API, consistency стакана и временные метки. Last price или цена в портфеле не заменяют исполнимый bid для SELL и ask для BUY.

Сохрани snapshot_id, frame.captured_at, book.captured_at, TTL, wall-clock времени получения/оценки. Считай возраст со знаком и достаточной точностью; свежий frame не омолаживает старый стакан. `age_ms=0` в журнале не доказывает отсутствие будущей метки: код может обрезать отрицательное значение.

Собери индикаторы того же snapshot: адаптивные пороги и source, последовательность завершённых свечей, SMA, диапазон, тренд. Количество 20+ свечей не доказывает непрерывность последних 20 минут.

### 3. Сверить с настройками и состоянием стратегии

Используй effective-настройки работающего контейнера и `strategy_snapshot` конкретного решения; отдельно сравни с `.env`/Compose. Изменение `.env` не меняет уже работающий процесс. Старый decision и новые настройки не являются одновременным конфликтом без хронологии.

Проверь guards до стратегии: lifecycle, свежесть/структура рынка, active intent, commission profile, доступность торговли, общий cash и резервы. Затем воспроизведи установленный кодом приоритет stop-loss → полный net take-profit → частичный выход → покупка/усреднение → WAIT. Уточни порядок по текущей реализации, включая `sell_armed`, pending_low и cooldown.

Считай Decimal, указывай единицы и знак. Учитывай комиссии входа оставшихся лотов и выхода, LIFO, минимальный размер заявки и округление. Не подменяй среднюю цену брокера LIFO-средней интерфейса. Резервные проценты окружения не заменяют реально применённые адаптивные пороги.

### 4. Найти фактическое решение в журналах

Выгрузи ограниченный по времени/количеству decision и business-audit журнал. Свяжи цепочку по automation_id + process_id, при наличии — snapshot_id, intent_id, sequence_number и revision. Запиши decision, reason_code, входные цены/количества, настройки и результат доставки/исполнения.

В этой архитектуре бизнес-аудит хранится в Worker SQLite и Core PostgreSQL; Docker stdout с HTTP 200 не является журналом решений. Подробная карточка API также может не содержать audit. Не объявляй зависание только по отсутствию stdout-сообщений.

Сравни ожидание с фактом **на входах момента решения**. Текущая котировка не доказывает ошибочность старого WAIT. Для текущего состояния отдельно укажи свежесть и допустимые действия. Если свечи, range/cycle или исходные timestamps решения не сохраняются, обозначь неполную проверяемость; не восстанавливай их текущими значениями.

### 5. Выявить аномалии и причины

Разделяй:

- ожидаемую защиту: stale/unavailable рынок, закрытые торги, неподтверждённое окно, cooldown, недостаток cash;
- доказанное расхождение данных/контрактов или воспроизведённый дефект;
- недостаток наблюдаемости, когда корневая причина ещё не доказана.

Ищи конкретную цепочку: вход → guard/ветка → decision → intent → брокерский ответ → факт → ACK/Core. Для Core/Worker drift проверь envelope, revision/sequence и принятие факта. Один свежий PENDING без retries — нормальная очередь, не доказательство сбоя.

Для `FUTURE_ORDER_BOOK` нужна пара времён одного snapshot и точка сравнения: clock skew, получение более новой котировки и разные часы guards — разные гипотезы. Для пустого Core при локальных лотах проверь bootstrap и факт позиции, не ограничивайся успешным reconciliation.

### 6. Оформить результат

Таблица: инструмент, broker/Core/Worker lots и state, цены и их время, effective/adaptive параметры, ожидаемый guard/decision, фактический reason/process_id/time, вердикт/ограничение.

Для каждой аномалии создай локальную задачу в `develop/reports/<audit-id>/tasks.md`: важность, файл/место, сценарий, ожидаемое/фактическое, точные ссылки на журнал и ID/время, доказанная причина отдельно от гипотез, рекомендуемое исправление и критерии приёмки на изолированной проверке. Если причины недостаточно — задача на диагностику с недостающими данными, не вымышленный дефект стратегии. Публикация задач во внешний трекер требует соответствующей авторизации.

Подтверждай «работает как ожидается» только для позиций/решений и интервала, для которых хватает доказательств. При аномалиях или пробелах не выдавай общий положительный вердикт. Укажи рецензента, область независимого кросс-ревью, результат и ограничения; существенные замечания к самому аудиту исправь до завершения.
