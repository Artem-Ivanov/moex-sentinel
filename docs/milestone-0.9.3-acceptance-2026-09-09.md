# Приёмка 0.9.3: проверка устойчивости и производительности

Реализация, регрессия и локальное развёртывание завершены 2026-09-09. Веха закрывает остатки 0.1/0.6,
добавляет воспроизводимый benchmark и фиксирует ограниченное наблюдение runtime.
Это базовые измерения; production SLA и длительная устойчивость не подтверждены.

## Исправления

Benchmark на шести инструментах обнаружил голодание очереди: планировщик
расходовал лимит брокера до вычисления решения. Первые два инструмента после
BUY возвращали WAIT, но продолжали занимать доступную ёмкость; остальные
постоянно получали `BROKER_RATE_LIMIT_BUDGET`.

Теперь `PositionBatchSchedulerService` сначала вычисляет решение и резервирует
ёмкость только для `BUY_MORE`, `SELL_PART`, `SELL_ALL`. WAIT/NO_ACTION сохраняют
вычисленное состояние без расходования лимита. Сам лимит и его пополнение не
менялись; при отклонении активного решения сохраняется прежняя семантика WAIT.
Резервирование остаётся консервативным: последующая отмена исполнения другими
проверками не возвращает токен. Тесты проверяют шесть позиций на трёх тактах и
ограничение допуска для каждого из трёх активных видов решений.

`BootstrapResult` переведён с frozen dataclass на frozen Pydantic DTO.
В `src` нет декораторов `@dataclass`; `@dataclass_transform` остаётся типовой
аннотацией базовых DTO. Поведение bootstrap, атомарность и повтор проверены.

Браузерная приёмка выявила выход `/brokers` за границы мобильного экрана.
Responsive CSS переносит группы статусов/действий и располагает карточку
вертикально на узком экране. Проверены ширины 320/390 px.

## Воспроизводимый benchmark

[Запуск и границы измерений](../develop/benchmarks/README.md),
[машинный результат](../develop/reports/runtime-benchmark-2026-09-09.json).

Используются реальные Analytics ASGI, Worker composition, файловая SQLite/outbox
и Core ingress на отдельной временной SQLite. Брокер и рынок синтетические;
конфигурация стратегии явно задана, рабочие настройки и базы не используются.

Начальные BUY/FILLED всех инструментов и три прогревочных такта исключены из
статистики. Затем выполняются **100 измеряемых тактов** на каждом размере,
по 20 завершённых свечей на инструмент. Проверяется, что все 600/2000/5000
измеряемых решений — WAIT/NO_THRESHOLD и новых заявок в этом интервале нет.

| Инструменты | Tick p50, мс | Tick p95, мс | Tick p99, мс | Delivery p95, мс | Решений/с с доставкой |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 6 | 65,50 | 88,14 | 111,73 | 93,40 | 39,31 |
| 20 | 238,78 | 297,90 | 339,21 | 333,75 | 35,80 |
| 50 | 521,73 | 590,90 | 705,32 | 1060,18 | 32,91 |

Tick включает Analytics, решения, сохранение и ожидание tracking; delivery —
последующее опустошение очереди через Core, включая диагностические COUNT
между batch. Producer и drain выполняются последовательно. p50 — медиана,
p95/p99 — nearest rank; 100 точек дают ограниченную оценку хвоста распределения.
Замеры сделаны на общей машине macOS/Python 3.12.7 при работающем Compose;
короткие регрессионные проверки также выполнялись во время наблюдения.

При потере ответа после Core commit проверены сохранение очередей 54/180/450
фактов при перезапуске, неизменный replay и итоговое опустошение. Число решений
Worker/Core совпало: 648/2300/6500. Повторных брокерских заявок нет.
Неподтверждённый outbox блокирует новые решения через hydration, поэтому
дополнительный такт без доставки не обязан увеличивать очередь.

Синтетические логические часы, SQLite и управляемый перезапуск не моделируют
сетевые задержки, PostgreSQL, частоту реальных заявок, BUY/SELL burst или убийство
процесса внутри commit. По этим данным нельзя объявить предел production-нагрузки
или обосновать перенос Worker на PostgreSQL. Доставка — заметная часть стоимости
данного теста; оптимизации требуют профиля рабочего Core PostgreSQL.

короткие события; когорта Analytics фиксируется при старте. Десятиминутная
выборка не является длительным soak-тестом или доказательством непрерывной свежести.

## UI и регрессия

[Browser smoke](../develop/scripts/check_brokers_ui.mjs) запускает настоящий
Chrome/Playwright на собранном frontend с имитацией API. Проверены пустой список,
форма, восстановление после 422, сохранение, выбор, редактирование/отмена,
переход к счетам и обратно, мобильная ширина и отсутствие JavaScript-ошибок.
Рабочий UI дополнительно проверен только GET/HEAD; реальные записи не менялись.
[Результат](../develop/reports/brokers-ui/result.json) и снимки относятся к явно
разделённым mock/runtime сценариям; screenshots сделаны только с синтетикой.
Скрипт записывает running/passed/failed и времена, чтобы старый PASS не скрывал
ошибку нового запуска.

- Полная регрессия приложения и `develop/tests`: **1015 passed**, 17 существующих
  предупреждений SDK/Starlette, PostgreSQL-тесты включены без пропусков.
- Frontend: **74 passed**, TypeScript и production build успешны.
- Ruff/Black: девять изменённых/новых Python-файлов; mypy Worker composition —
  без ошибок для одного явно проверенного файла.
- PostgreSQL использовался только в одноразовом контейнере с tmpfs на порту
  localhost 55439; контейнер после проверки остановлен и удалён. Временные
  benchmark SQLite удалены.
