# Приёмка 0.9.7: объединённое чтение идентичности факта

Веха завершена 2026-09-10: реализация, полная регрессия, основной профиль,
контрольные пробы, обновление Core и итоговое независимое ревью проверены.
[Согласованный объём](milestone-0.9.7-envelope-lookup.md).

## Изменение

`TradingAuditPort.find_envelope_matches` заменяет два отдельных чтения
envelope в ingress. Репозиторий выполняет один SELECT с условием
`scope AND (event_id OR (automation_id AND sequence_number))` и возвращает
все совпавшие DTO через прежний mapper. Event может принадлежать другому
автомату в том же scope. Две ветки могут найти две разные строки; `scalars()`
сохраняет обе, а ingress классифицирует результат независимо от порядка строк.

Event имеет прежний приоритет перед sequence. Точный повтор сравнивается
целиком, кроме received_at, и подтверждается без повторного применения факта.
Ограничения БД, append/CAS, revision/sequence/gap, UTC и транзакции групп
сохранены. Пакетного предварительного чтения и промежуточного кэша нет.

## Проверки

Первый SQLite-прогон дал 11 ожидаемых падений и 5 прошедших характеристических
проверок: отсутствовал новый lookup, а production ingress на exact replay
выполнял три запроса вместо двух. PostgreSQL после исправления тестовой
фикстуры дал 12 ожидаемых падений из-за отсутствия lookup. Фикстура теперь
задаёт короткий синтетический ticker вместо UUID, превышающего VARCHAR(32).
После реализации те же проверки и существующий набор ingress/API прошли:
**61 passed, 17 прежних предупреждений**.

Полная регрессия на отдельном временном PostgreSQL с мигрированными схемами:

```bash
POSTGRES_TEST_DATABASE_URL='postgresql+psycopg://sentinel_test@127.0.0.1:60861/sentinel_test' \
  .venv/bin/pytest -q tests develop/tests --tb=short
```

**1152 passed, 17 warnings, 39,05 секунды**, без пропуска PostgreSQL-тестов.
Предупреждения относятся к существующим deprecated полям SDK и совместимости
Starlette/httpx. Ruff и Black проходят по семи затронутым Python-файлам.
Один прежний тест двух lookup заменён расширенной матрицей; добавлено 28 тестовых
случаев, поэтому итоговый прирост относительно 1125 составляет 27.

- [Общий контракт lookup](../tests/storage/test_envelope_lookup.py): 10 случаев
  на SQLite и те же 10 на PostgreSQL. Проверяются 0/1/2 строки, обе идентичности,
  границы scope/automation, payload, время и бюджет одного запроса.
- [Production ingress](../tests/services/test_ingress_envelope_lookup.py):
  exact replay за два SELECT без записей, duplicate внутри группы, приоритет
  event при двух совпадениях (в том числе другого автомата), replay вместе с
  новым фактом, rollback группы и сохранение успешной соседней группы.
- [Гонки PostgreSQL](../tests/integration/postgresql/test_envelope_lookup.py):
  Barrier после обоих lookup гарантирует конкуренцию реальных транзакций.
  Проверяются единственная фиксация, rollback audit payload проигравшего,
  повтор победителя и исправленная доставка проигравшего.

Существующая классификация проигравшего exact-race сохранена: при гонке INSERT
ошибка PK может дать retryable TEMPORARY_CORE_FAILURE; при чтении envelope
после commit победителя CAS даёт AUTOMATION_REVISION_CONFLICT. Последующий
точный replay успешен. Изменение этой классификации не входит в 0.9.7.

## Независимое ревью кода

Автор production-кода и SQLite-тестов — root; независимый рецензент —
`next_scope_review`. Проверены SOLID, узкий порт, состав OR-предиката, оба
совпадения, приоритет конфликтов, DTO, транзакции, гонки и достаточность тестов.
Рецензент независимо выполнил 49 SQLite/API-проверок: все прошли.
Результат ревью кода — **APPROVED**, открытых замечаний нет.

PostgreSQL-набор реализовал `next_scope_review`; root независимо проверил
фикстуры, синхронизацию, ограничение ожиданий, допустимые исходы гонки и rollback,
затем выполнил RED/GREEN и полную регрессию на отдельном экземпляре.

## Условия сравнительного профиля

```bash
bash develop/scripts/profile_postgresql.sh --instruments 6 20 50 --warmup 3 --iterations 100 --batch-size 100 \
  > develop/reports/postgresql-profile-envelope-2026-09-10.json
.venv/bin/python develop/reviews/milestone-0.9.7/compare_profiles.py
```

Baseline — [профиль 0.9.6](../develop/reports/postgresql-profile-cas-2026-09-09.json).
Runner создаёт собственный PostgreSQL на tmpfs с динамическим loopback-портом;
в каждом сценарии используется отдельная схема Alembic head. Синтетические
брокер и рынок проходят настоящий Worker SQLite → CoreClient TCP HTTP → Core
PostgreSQL. Все 100 измеряемых тактов должны быть WAIT/NO_THRESHOLD; начальные
BUY/FILLED и восстановление после потерянного ACK измеряются отдельно.

Это отдельные прогоны в разные дни на общей машине с работающим Compose,
без чередования версий. Count SQL проверяется точно; различия latency зависят
также от нагрузки среды. tmpfs не моделирует fsync постоянного диска.
Production SLA, SELL burst, предел параллельной нагрузки и длительная
доступность рынка этими измерениями не подтверждаются.

## Контроль latency и плана запроса

Из-за ухудшения исторического сравнения выполнен дополнительный
[ABBA-контроль](../develop/reports/postgresql-profile-envelope-abba-2026-09-10.json).
[Скрипт](../develop/reviews/milestone-0.9.7/paired_profile.py) загружает сохранённые
до реализации методы ingress/repository только внутри процесса benchmark.
Каждый вариант использует новую мигрированную Core-схему и Worker SQLite;
после случая исходные методы восстанавливаются. Рабочие файлы не переключаются.
На одном временном PostgreSQL: 20 инструментов, warmup=3, 30 WAIT-тактов,
batch=100; порядок before → after → after → before.

| Порядок / вариант | SQL на решение | Drain p50/p95/p99, мс | Решений/с с доставкой |
| --- | ---: | ---: | ---: |
| 1 / before | 103 | 1314,56 / 1502,81 / 1526,25 | 13,06 |
| 2 / after | 94 | 1508,13 / 2102,63 / 2142,87 | 11,33 |
| 3 / after | 94 | 977,35 / 1385,60 / 1729,27 | 15,54 |
| 4 / before | 103 | 1608,07 / 1924,42 / 1929,20 | 11,07 |

Каждая строка — 600 WAIT-решений / 5400 фактов; состав нагрузки, один потерянный
ACK, сохранность envelopes, пустой конечный outbox и отсутствие повторных
SDK-входов проверены. Контроль показывает заметный разброс и разнонаправленные
сравнения. Он не воспроизводит историю 50 инструментов / 100 тактов и не
исключает регрессию в этом объёме. Устойчивого эффекта на end-to-end latency
по нему не заявляется; причина роста в основном профиле не установлена.

Дополнительно [проверен план на 50 000 событий](../develop/reports/postgresql-profile-envelope-query-plan-2026-09-10.json):
50 автоматов × 1000 envelopes, новый отсутствующий event/sequence.
[Проба](../develop/reviews/milestone-0.9.7/query_plan_probe.py) создаёт и удаляет
собственную схему на отдельной тестовой БД. До и после ручного ANALYZE OR
использует BitmapOr по `automation_events_pkey` и
`uq_automation_events_scope_sequence`; полного сканирования нет. В EXPLAIN
запрос выполнялся за 0,033/0,034 мс; это единичные планы, а не latency SLA.

После прогрева и ANALYZE выполнены 150 чередующихся пар реальных repository-вызовов:

| Вариант | SQL всего | Lookup p50/p95/p99, мс |
| --- | ---: | ---: |
| Два прежних чтения | 300 | 0,725 / 0,966 / 1,029 |
| Одно объединённое | 150 | 0,401 / 0,521 / 0,549 |

Схема этой пробы создана из Base metadata, payload синтетический, одна прогретая
Session. Это проверка конкретного lookup, а не замена полного ingress-профиля.
План и измерения не подтверждают гипотезу замедления самого lookup из-за большой
истории, но не доказывают ускорение всей цепочки.

Веха оценивает доказанное сокращение SQL при сохранении контрактов. Результат
по latency остаётся ограничением: для утверждения о производительности полной
цепочки нужен отдельный контролируемый профиль нужной нагрузки и целевой порог.

## Обновление локального Core и границы runtime-проверки

Образ backend собран и установлен через Compose. На время пересоздания Core
Worker остановлен; после успешного healthcheck и перезагрузки nginx он запущен
с прежним SQLite volume. `/api/health` после обновления вернул `status=ok`,
`database=ok`, `schema=compatible`. SHA-256 всех трёх изменённых модулей,
импортированных внутри контейнера, совпали с проверенными исходниками.

Профильный runner удалил свой контейнер, контрольная проба удалила свою схему,
отдельный тестовый контейнер остановлен и удалён. Рабочие persistent volumes
сохранены. Повторная полная регрессия после развёртывания не выполнялась:
проверена версия кода в образе и доступность Core. Живые торговые данные и
рабочие таблицы отдельно не исследовались, непрерывность рыночного потока
или свежесть всех инструментов этим healthcheck не подтверждаются.

## Итоговое независимое ревью

Рецензент `next_scope_review` независимо сверил пять актуализируемых документов,
основной JSON и comparison, четыре ABBA-результата и пробу плана. Подтверждены
SQL count, проценты, опубликованные квантили, throughput, recovery-инварианты
и согласованность границ приёмки. Предыдущее одобрение production/SQLite-кода
сохраняется; диагностическую пробу автора `next_scope_review` проверил и
выполнил root. Runtime-проверки выполнил root; рецензент оценил соответствие
выводов их охвату, не заявляя собственного повторного runtime-прогона.

Результат — **APPROVED**, существенных и открытых замечаний нет. Редакционное
замечание о дате фазы 0 исправлено. После оформления прошли шесть проверок
документации/архитектуры, 75 локальных ссылок разрешаются; Black проходит по
10 Python-файлам, Ruff — по production, тестам и вспомогательным пробам.
