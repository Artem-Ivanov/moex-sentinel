# Приёмка вехи 0.7 — единая динамическая стратегия

Статус: реализация, проверки и локальное развёртывание завершены.

## Согласованный объём

Для всех позиций применяется один определённый кодом алгоритм. Analytics
пересчитывает шаг усреднения и порог частичной чистой прибыли по рынку.
Стратегия не хранится как настраиваемая сущность БД и не назначается позиции.
По уточнению пользователя новые поля ресурсов не вводятся: сохраняются общий
размер покупки, проверка свободных средств и резервы активных заявок.

`decision.strategy_snapshot` сохраняет исходные настройки решения,
`decision.indicators` — фактически применённые адаптивные значения и источник.
Эти исторические данные не являются редактируемым шаблоном стратегии.

## Изменения

Единая идентичность `ADAPTIVE_SCALPING / 1.0` определена в
`sentinel_contracts.strategy`. Её используют класс стратегии, materializer,
Core API и новые записи bootstrap-аудита. Ранее API и bootstrap сообщали
`adaptive_scalping / 1`, тогда как решения Worker уже использовали
`ADAPTIVE_SCALPING / 1.0`. Поля API и формат снимка решения сохранены;
существующие записи истории не переписывались.

Описание в карточке позиции и документация объясняют динамические пороги.
Дорожная карта исправлена по согласованному объёму. Формулы адаптации,
комиссии, размер покупки, TTL, резервирование и схема обеих БД не менялись.

## Проверки

- Python: 925 тестов в `tests` без `tests/integration/postgresql`.
  PostgreSQL-проверки не повторялись: миграций и изменений схемы в этой вехе нет.
- Отдельно семь новых сквозных сценариев
  `tests/integration/test_dynamic_strategy_contract.py`.
- Frontend: 74 теста, TypeScript и production build.
- Ruff и Black для изменённых Python-файлов; `git diff --check`.
- Docker-образы Core, Worker и frontend успешно собраны.

Для исправления идентичности сначала получены два ожидаемых падения API и
bootstrap-тестов, затем 35 связанных тестов прошли. Новые сквозные тесты
закрепляют уже существующее динамическое поведение:

- При неизменной цене снижение рассчитанного шага меняет ожидание разворота
  на BUY; снижение порога чистой прибыли разрешает SELL_PART.
- Последовательность ADAPTIVE → fallback → ADAPTIVE обновляет фактические
  показатели. Проверяются пустая история, 14/15/19 свечей и разрыв окна 20.
- После повторного открытия Worker SQLite и следующего расчёта ранее
  сохранённые решения Worker/Core и заявки Core остаются неизменными.
- Решения и исполнения проходят настоящие materializer, durable outbox,
  Core ingress и подтверждение доставки на тестовых БД.

Ограничение тестов: один инструмент с несколькими рыночными поколениями,
Analytics HTTP через ASGI, Core ingress вызывается непосредственно;
Worker использует временную SQLite, Core — SQLite в памяти. Внешний брокер
синтетический. Многопозиционные пакеты, stale TTL и outage/recovery проверены
существующей регрессией. Есть 17 прежних предупреждений устаревания зависимостей.

## Локальное окружение

Worker штатно остановлен с ожиданием до 60 секунд, затем обновлены Core,
frontend и Worker. Существующие PostgreSQL и SQLite volumes сохранены;
миграции данных не требовались.

После обновления все шесть Compose-сервисов работают; четыре настроенных
healthcheck проходят. Core health подтверждает совместимость схемы.
В публичном API идентичность стратегии согласована у всех шести автоматов.

В окне 12:30:41–12:30:48 UTC Worker создал 14 новых решений. UNAVAILABLE
не было, в последнем замере все шесть инструментов FRESH, проверка завершилась
с кодом 0. В остальных семи замерах отдельные стаканы были STALE: максимум
возраста 6626 мс. История содержала 100–120 свечей, максимальная задержка
HTTP — 41 мс. Это подтверждение восстановления работы, а не непрерывной
свежести всех шести инструментов; ограничение внешнего потока описано
в приёмке 0.5. Активных незавершённых intent в этом окне не было.

После этого очередь фактов наблюдалась пустой; спустя пять секунд содержала
47 новых ожидающих фактов. Максимальный сохранённый `retry_count` равен нулю;
этот счётчик не исключает повторов HTTP внутри одного вызова доставки.
