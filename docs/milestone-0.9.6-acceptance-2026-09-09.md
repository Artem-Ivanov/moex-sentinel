# Приёмка 0.9.6: UPDATE RETURNING вместо повторного чтения

Веха завершена 2026-09-09: реализация, регрессия, сравнительный профиль и обновление Compose проверены.
[Постановка](milestone-0.9.6-core-sql-roundtrips.md) ограничивает изменение
успешными accept-фактами и сохранением существующего CAS-контракта.

## Изменение и корректность

`AutomationFactsRepository.accept_supporting_fact` и `accept_state_fact`
возвращают полную строку автомата через UPDATE RETURNING и преобразуют её
существующим mapper в DTO. Дополнительный SELECT на успешном пути удалён.
Предикаты scope/id/revision/sequence, транзакция группы и порядок фактов сохранены.

`populate_existing=True` обновляет уже загруженную ORM-сущность из результата
БД, включая lifecycle/bootstrap и UTC-время. `synchronize_session=False`
исключает изменение объекта в памяти по вычисленным условиям, если UPDATE
фактически не затронул ни одной строки.

Тест выявил сопутствующий дефект неуспешного CAS: устаревший объект в identity map
искажал различение REVISION_CONFLICT и SEQUENCE_CONFLICT. Диагностический helper
теперь читает scoped scalar revision непосредственно из БД; отсутствие строки
по-прежнему даёт NOT_FOUND. Это чтение требуется только при неуспешном CAS.

Начальный RED дал пять падений: три проверки полного актуального состояния и
две проверки лишнего SELECT. Отдельный RED дал ещё два падения классификации
конфликта при устаревшем ORM-объекте. После исправления те же сценарии проходят.

## Проверки

Полная регрессия на отдельном PostgreSQL:

```bash
POSTGRES_TEST_DATABASE_URL='postgresql+psycopg://sentinel_test@127.0.0.1:55439/sentinel_test' \
  .venv/bin/pytest -q tests develop/tests --tb=short
```

**1125 passed, 17 warnings, 39,75 секунды.** Предупреждения относятся к прежним
deprecated полям SDK и совместимости Starlette/httpx.

- [Общий контракт SQLite](../tests/storage/test_automation_fact_returning.py):
  полный DTO, UTC/миллисекунды, lifecycle/bootstrap, устаревший identity map,
  последовательные accept в одном UoW, отсутствие дополнительного SELECT,
  классификация ошибок и rollback группы.
- [PostgreSQL](../tests/integration/postgresql/test_automation_fact_returning.py):
  тот же контракт на мигрированной отдельной схеме и гонки двух независимых
  транзакций с заранее прочитанным состоянием. Ровно один победитель; проигравший
  получает SEQUENCE_CONFLICT для supporting либо REVISION_CONFLICT для state.
- Существующие ingress/lifecycle и HTTP/PostgreSQL benchmark-тесты проходят,
  включая exact replay после потерянного ответа и восстановление Worker.

Ruff и Black проходят по трём изменённым Python-файлам. Внешний mypy 1.20.2
с `--python-executable .venv/bin/python` проходит по изменённому repository.
Это проверка данного файла, не заявление о полном mypy-gate проекта.

## Сопоставимость профиля

```bash
bash develop/scripts/profile_postgresql.sh --instruments 6 20 50 --warmup 3 --iterations 100 --batch-size 100 \
  > develop/reports/postgresql-profile-cas-2026-09-09.json
```

Стенд, команда и алгоритм измерения сохранены из 0.9.4. Новый файл не заменяет
[baseline JSON](../develop/reports/postgresql-profile-2026-09-09.json).
Сравниваются 100 WAIT-тактов на 6/20/50 инструментах, три warmup, batch=100,
deadline=0 и последовательный Worker SQLite → TCP HTTP → Core PostgreSQL.
Начальные BUY/FILLED и проверка потерянного ACK находятся в отдельных разделах.

Это последовательные прогоны на общей машине при работающем Compose, без
рандомизированного чередования версий. Полная регрессия завершена до измерений.
PostgreSQL использует tmpfs; commit-задержки не отражают постоянный диск.
Сокращение SQL проверяется точно, разницу latency следует интерпретировать
с учётом шума среды. Production SLA и перенос Worker на PostgreSQL не оцениваются.

## Независимое ревью

Автор — `cas_returning_implementation`; рецензент — `pg_profile_implementation`,
который не реализовывал CAS-изменение. Проверены SOLID, границы repository,
identity map, конфликты, UTC, rollback, replay и достаточность тестов.
Рецензент независимо выполнил 25 PostgreSQL-тестов с конкурентными транзакциями
и 48 SQLite/ingress-проверок. Результат ревью кода — **APPROVED**.

Рецензент отдельно пересчитал три JSON, проверил параметры стенда, все размеры
выборок, порядки квантилей, SQL-разницу и восстановление: замечаний нет.
Итоговое ревью интеграции — **APPROVED**: проверены все строки четырёх таблиц
по исходным JSON, runtime-наблюдения, ссылки и согласованность статусов пяти
документов. Существенных и прочих открытых замечаний нет.

## Проверка рабочего Compose

Образ backend пересобран и обновлён с успешным healthcheck; nginx перечитал
конфигурацию. Worker остановлен на время обновления Core и запущен с прежним
SQLite volume. `/api/health` вернул `status=ok`, `database=ok` и совместимую схему.
Все шесть сервисов запущены; analytics, backend, database и frontend имеют
статус healthy. Временные контейнеры профильного и регрессионного PostgreSQL
удалены, рабочие persistent volumes сохранены.

[Агрегированный runtime-пробник](../develop/reports/runtime-cas-check-2026-09-09.jsonl)
за 6,21 секунды зарегистрировал 10 новых решений Worker; время последнего решения
продвинулось, outbox пуст на обеих границах наблюдения. Во всех четырёх запросах
доступны шесть инструментов, Analytics unavailable = 0, набор и профиль совпадают.
В третьем запросе все шесть прошли строгую проверку свежести; в остальных прошли
3/3/4, а неподходящие стаканы отклонены с STALE_ORDER_BOOK/FUTURE_ORDER_BOOK.
Это короткое подтверждение работы после обновления, не доказательство непрерывной
свежести рынка или длительного SLA. Полный набор тестов проверен до развёртывания;
после документирования отдельно проходят шесть проверок документации и архитектуры.
