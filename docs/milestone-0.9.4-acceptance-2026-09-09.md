# Приёмка 0.9.4: профиль доставки фактов на PostgreSQL

Веха завершена 2026-09-09: профиль, регрессия и решение о следующем объёме.
Объём — первый этап
[постановки](phase-1-implementation-plan.md): измерения и решение о следующем
объёме оптимизации. Целевой production SLA не задан и не оценивается.

## Воспроизводимость и границы

```bash
bash develop/scripts/profile_postgresql.sh --instruments 6 20 50 --warmup 3 --iterations 100 --batch-size 100 \
  > develop/reports/postgresql-profile-2026-09-09.json
```

[Runner](../develop/scripts/profile_postgresql.sh) сам создаёт отдельный
PostgreSQL 16 Alpine с динамическим loopback-портом, ждёт готовности и удаляет
свой контейнер после успеха или ошибки. В каждом сценарии новая случайная схема
с миграциями Alembic head; удаляется только она. Рабочая БД, volumes и окружение
с credentials не используются. Стратегия явно задана в синтетическом стенде.

Используются реальные Analytics ASGI, Worker composition с файловой SQLite,
CoreClient, TCP HTTP production endpoint `/internal/automation-facts`,
TradingFactIngressService, mapper, UoW и PostgreSQL repositories. Брокер и рынок
синтетические. HTTP сервер стенда включает production router с внедрёнными
usecase-зависимостями; полное приложение Core и фоновые службы не запускаются.

Сценарии последовательны: producer → explicit drain. Один источник, аккаунт и
HTTP worker; batch=100 фактов, deadline=0, внутренние повторы доставки=0.
Подбор batch штатный: Worker сохраняет начальную bootstrap-четвёрку вместе,
обычные факты одного автомата могут попасть в разные batch. Core атомарно
обрабатывает группу автомата внутри полученного запроса. В этом профиле автоматы
начинают в IN_WORK, без bootstrap открытой позиции. Три warmup
исключены из измеряемого WAIT. Начальные BUY/FILLED и промежуточные WAIT при
ограничении двумя заявками на такт вынесены в отдельный профиль.

Длительности измерены `perf_counter`, доменные часы переходят на минуту за такт.
Это не тест TTL при реальном ожидании и не модель заявочного burst. PostgreSQL
работает на **tmpfs**: замер DBAPI COMMIT не характеризует fsync/IOPS или задержки
постоянного production-диска. На машине продолжал работать обычный Compose;
полная регрессия выполняется после замера, чтобы не создавать дополнительную
конкурирующую нагрузку.

## Значение метрик

Определения и размеры выборок находятся в
[README профилировщика](../develop/benchmarks/README.md). p50 — медиана,
p95/p99 — nearest rank; 100 тактов дают ограниченную оценку хвоста распределения.

Решение включает получение Analytics, подготовку, сохранение и ожидание tracking.
Очередь измеряется от создания ORM-строки outbox до первой отправки, включая
оставшееся ожидание commit Worker. HTTP roundtrip включает сериализацию клиента,
TCP, router/ingress и разбор ответа. SQL execution и DBAPI COMMIT измеряются
внутри ingress, Session.commit отдельно включает flush. Диагностические COUNT,
seed, миграции и pool pre-ping не входят в счётчик SQL внутри ingress.

Разность суммарного HTTP и суммарного ingress характеризует совокупные накладные
расходы клиента, HTTP/router и транспорта. Она не является чистой сетевой
задержкой. Вложенные длительности нельзя складывать; разность p95 двух этапов
не является p95 их разности. Сумма ожиданий отдельных фактов также не равна
времени выполнения всего последовательного сценария.

## Восстановление после потери ответа

После успешной транзакции production endpoint ASGI-обёртка обрывает тело HTTP
ответа. Настоящий CoreClient получает ошибку транспорта. Перед перезапуском
проверяется, что соответствующие события уже записаны в Core PostgreSQL, а
исходные envelopes остаются в Worker SQLite. Затем Worker штатно закрывается
и открывает прежнюю БД; сравнивается неизменность envelopes до/после перезапуска
и повторной доставки, итоговые Core-события, решения, заявки и опустошение outbox.
Счётчик входов в SDK увеличивается до проверок синтетического брокера.

Сценарий подтверждает replay после неоднозначного HTTP-результата. Он не моделирует
kill процесса внутри commit, отказ диска или восстановление неопределённого
брокерского исполнения — это отдельные контрактные проверки других вех.

Commit приходится на группу автомата внутри полученного batch, а не обязательно
один раз на решение. Обычные факты одного автомата могут доставляться несколькими
запросами. Размеры выборок очереди: 5400 / 18000 / 45000 фактов.
В синтетическом такте время общее для всех автоматов; writer упорядочивает факты
автомата с шагом 1 мс, а outbox сортируется по времени/event_id. При batch=100
девять фактов автомата распределяются между 1/2/5 HTTP-запросами для 6/20/50
инструментов. Каждый затронутый автомат получает отдельный get/commit в каждом
запросе. Это объясняет дополнительные 1/4 SQL-вызова на решение относительно
профиля на шести инструментах; алгоритм не является явным round-robin.

## Вывод и следующий объём

По суммам измерений drain занимает **82,08–84,76%** времени последовательной
цепочки. SQL cursor execution занимает **65,45–69,64%** ingress; это включает
обмен драйвера с PostgreSQL, а не только вычисления сервера БД. Время HTTP вне
ingress составляет **0,62–0,78%** суммарного HTTP. Поэтому подтверждённый первый
кандидат оптимизации — число обращений к БД внутри Core. Эти доли не являются
независимыми частями одной суммы и не обосновывают изменение сетевого протокола.

В WAIT получено 66 600 / 224 000 / 575 000 SQL-вызовов, то есть **111 / 112 / 115
на решение**. Разбор исходников подтвердил повторный SELECT автомата после
успешного CAS UPDATE в `accept_supporting_fact`/`accept_state_fact`: UPDATE уже
возвращает id, затем repository делает `get`. Также отдельно читаются envelopes
по event/sequence и scoped references; их оптимизация требует сохранения проверок
идентичности и области данных.

Следующий ограниченный шаг — [0.9.6: сокращение повторных чтений Core](milestone-0.9.6-core-sql-roundtrips.md).
Начать с возврата актуального состояния непосредственно из UPDATE RETURNING,
сохранив CAS, диагностику конфликтов, DTO/UTC и атомарность группы. Сначала
подтвердить сокращение запросов тем же профилем, затем оценить фактическую задержку.
Ускорение заранее не заявляется. Переход Worker на PostgreSQL не обоснован.

## Проверка реализации

Полная регрессия на отдельном PostgreSQL:

```bash
POSTGRES_TEST_DATABASE_URL='postgresql+psycopg://sentinel_test@127.0.0.1:55439/sentinel_test' \
  .venv/bin/pytest -q tests develop/tests --tb=short
```

**1077 passed, 17 warnings, 33,73 секунды.** Предупреждения относятся к ранее
существовавшим deprecated полям SDK и совместимости Starlette/httpx. В числе
проверок — настоящий HTTP/PostgreSQL с batch=2/100, потерей ACK и restart,
учёт попытки дублирующего dispatch, cleanup при ошибке закрытия клиента,
runner при успешном запуске и отказах benchmark/старта контейнера.
Ruff и Black проходят по всем пяти новым Python-файлам; `bash -n` проходит для
runner. После обновления документации дополнительно пройдены 9 проверок
документации, архитектуры и runner. Временные контейнеры профиля и регрессии
остановлены и удалены; итоговый Docker-фильтр `moex-sentinel-profile-` пуст.

`pg_profile_implementation` реализовал benchmark; `pg_profile_contract_audit`
независимо проверил контракт, SOLID, метрики, HTTP и владение ресурсами. Замечание
к cleanup исправлено: ошибка закрытия HTTP клиента не пропускает остановку
сервера; отдельный тест прошёл RED→GREEN. Root реализовал runner, тот же
независимый рецензент проверил изоляцию контейнера и cleanup.
Итоговое независимое ревью реализации, интеграции, чисел JSON/отчёта, ссылок,
статусов и постановки 0.9.6: **APPROVED**, существенных замечаний не осталось.

Применение профиля не требует изменения торгового runtime. Следующий объём
сформулирован в 0.9.6 с сохранением атомарности групп, revision/sequence,
точного replay и границ Core/Worker.
