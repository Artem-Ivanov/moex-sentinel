# Приёмка 0.3 — жизненный цикл Core и Worker

Дата: 2026-09-09. Статус: завершена; обновлённое локальное Compose-окружение запущено.

## Результат

- Core и Worker используют общую политику переходов с разными правами
  пользовательской команды и предложения Worker. CLOSED терминален;
  обычный HOLD возобновляется через пользовательский IN_QUEUE.
- Повтор команды не расходует ревизию. Повтор принятого события получает ACK;
  новый запрещённый state-факт отклоняет группу без частичных записей.
- Core защищает запись ревизией. Worker атомарно проверяет исходные
  state/revision/sequence перед изменением состояния, outbox и bootstrap-лотов.
  Конкурентное закрытие не перезаписывается устаревшим предложением.
- Интеграция использует настоящий HTTP app/CoreClient и отдельные Core/Worker
  хранилища. Проверены lifecycle, потерянный ACK, повтор доставки, авторитетные
  snapshots, запрещённый переход и откат группы.
- Hydration, решение и отправка заявки сохраняют один process_id.
  Восстановление UNCERTAIN имеет стабильную корреляцию всех audit-стадий.
  Сбой записи начального audit не подавляет повторную попытку восстановления.

## Развёртывание и ограничения

Worker остановлен штатно с exit code 0. Core, сборщик снимков и Worker
пересозданы из проверенных образов; nginx перечитал адрес backend.
Схема БД не менялась, оба существующих persistent volume сохранены.
API через frontend сообщает database=ok и schema=compatible.
Снимок портфеля доступен, ошибок сводки нет, стратегия включена.

На контрольном срезе четыре автомата IN_WORK и один HOLD, одинаково в Core
и Worker. HOLD и один UNCERTAIN intent существовали до обновления и сохранились
после штатного перезапуска. Обновление не считается подтверждением исполнения
этой заявки; её состояние не сбрасывалось и автомат принудительно не возобновлялся.
Обычный HOLD исключён из runtime-команд: для новой попытки сверки нужен явный
resume. Успех подтверждается терминальным состоянием intent и стадией
WORKER_RECOVERY_COMPLETED, а не одним перезапуском. После неоднозначной попытки
повторная сверка того же intent требует нового экземпляра recovery-сервиса;
повторять resume вслепую не следует.

Доставка после обновления подтверждена ростом суммарного sequence с 89 092
до 93 607. На втором срезе текущие pending-факты имели retry_count=0,
FAILED-фактов не было. Временный PostgreSQL тестов штатно остановлен и удалён.

OPENING сохранён в публичном enum и матрице. Lease/fencing для нескольких
Worker и новая стратегия не входят в эту веху. Время audit — момент записи
события, а не измеренная длительность стадии. Следующая веха — 0.8,
реструктурирование механики принятия решений.
