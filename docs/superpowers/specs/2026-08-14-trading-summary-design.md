# Сводка торговли и исторический P&L

## Статус

Согласовано и поставлено в очередь после завершения текущей runtime-вехи. Эта спецификация не разрешает удаление старых volumes и не меняет состояние торгового воркера.

## Цель

Переименовать страницу «Открытые позиции» в «Торговля» и добавить перед таблицей открытых позиций блок «Сводка». Сводка показывает по всем активным брокерским счетам:

- текущую стоимость портфеля;
- свободные денежные средства;
- торговый P&L за 24 часа, 7 суток и 30 суток.

Валюты агрегируются и показываются раздельно. Пересчёта по валютному курсу нет.

## Семантика P&L

Периодный P&L — изменение стоимости портфеля с учётом реализованного и нереализованного результата и комиссий, но без влияния пополнений и выводов:

```text
накопленный P&L =
  предыдущий накопленный P&L
  текущая стоимость портфеля
  - предыдущая стоимость портфеля
  - пополнения
  + выводы
```

Периоды скользящие: 24 часа, 7 × 24 часа и 30 × 24 часа. Для периода используется разница накопленного P&L между последним снимком и ближайшим снимком у начала периода. Пока полной истории нет, базой служит самый ранний снимок, а API возвращает признак неполного периода и фактическое начало расчёта.

## Фоновый сбор

Снимки собирает отдельный Compose-сервис `portfolio-snapshot-worker`. Celery и Redis не добавляются: для одной периодической задачи достаточно изолированного асинхронного процесса.

Сервис:

1. Каждые 60 секунд получает портфель и операции всех активных счетов.
2. Для каждого счёта и валюты находит предыдущий снимок.
3. Учитывает только исполненные операции пополнения и вывода между предыдущим и текущим снимками.
4. В одной транзакции записывает новый снимок с накопленным P&L.
5. Использует PostgreSQL advisory lock и уникальный минутный интервал, чтобы параллельный или повторный запуск не создавал дубликаты.

Интервал задаётся `PORTFOLIO_SNAPSHOT_INTERVAL_SECONDS`, значение по умолчанию — `60`. Временные ошибки брокера обрабатываются ограниченным exponential backoff. Ошибка одного счёта не блокирует остальные. Если невозможно надёжно получить денежные операции между снимками, снимок этого счёта не записывается: пополнение нельзя ошибочно считать прибылью.

Сбор аналитики не зависит от браузера, backend-процесса и торгового воркера. Остановка snapshot-worker не останавливает торговлю.

## Хранение

`portfolio_snapshots` хранит снимки отдельно по `user_broker_id`, `account_id` и `currency`. Каждая запись содержит стоимость портфеля, свободные средства, накопленный торговый P&L, UTC timestamp с точностью до миллисекунд и минутный bucket для идемпотентности.

Первый снимок получает накопленный P&L `0` и становится начальной точкой. Ограничение уникальности защищает пару «счёт + валюта + минутный bucket». Индекс по счёту, валюте и времени поддерживает выбор базовых снимков для трёх периодов.

## API

Новый read-only endpoint `GET /api/trading/summary` возвращает:

- `captured_at` последнего согласованного снимка;
- массив итогов по валютам;
- для каждой валюты `portfolio_value`, `free_cash` и три периода P&L;
- для каждого периода значение, `from`, `to` и `complete`;
- безопасные ошибки отдельных счетов, не скрывающие успешные данные остальных.

Endpoint читает только PostgreSQL и не обращается к брокеру в HTTP hot path.

## Интерфейс

Навигационный пункт и заголовок страницы называются «Торговля». Внутри страницы порядок блоков:

1. «Сводка» — карточки по валютам со стоимостью портфеля, свободными средствами и P&L за сутки, 7 дней и месяц.
2. «Открытые позиции» — существующая таблица и действия без изменения маршрута `/positions`.
3. «Последние операции» — существующая таблица.

Положительный P&L получает положительный визуальный статус, отрицательный — отрицательный, нулевой — нейтральный. Неполный период явно подписывается «данные с <дата>», а не маскируется под полный. При отсутствии первого снимка показывается `—`. Кнопка «Обновить» параллельно обновляет сводку, позиции и операции; частичная ошибка одного блока не очищает остальные.

## Проверка

- Unit-тесты формулы P&L для пополнения, вывода, комиссий, смены стоимости и неполной истории.
- Repository-тесты идемпотентного минутного bucket, блокировки и выборки базовых снимков.
- Service-тесты изоляции ошибок счетов, валют и повторных запусков.
- API contract-тесты полной и неполной истории, пустого состояния и частичных ошибок.
- Frontend-тесты нового названия, порядка блоков, валютных карточек, знака P&L, неполного периода и общей кнопки обновления.
- Compose smoke-test отдельного snapshot-worker без Redis и без зависимости торговли от его состояния.

## Вне объёма

- график капитала;
- конвертация валют;
- календарные периоды вместо скользящих;
- Celery/Redis и универсальная очередь фоновых задач;
- изменение торговой стратегии или существующего маршрута `/positions`.
