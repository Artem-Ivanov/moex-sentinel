## Выбранная схема

Два Compose project на имеющемся VPS: текущий Sandbox и новый PROD.
Core процессы используют существующий общий PostgreSQL volume и одну БД;
PROD не запускает второй database service. У каждого приложения свои env,
broker scope, операторские сессии и внутренние application сети. Доступ Core
к общей БД — через private data network. До первой PROD записи Sandbox backend
обновляется с полными scope guards. Worker durable volumes сохраняются до
отдельной миграции журнала исполнения. Один Worker на реальный счёт.
Sandbox ledger, event IDs, intent и account ID в PROD не копируются.
Общие исходники/images и PostgreSQL; Analytics остаётся без credentials.

Замер02.10 VPS:1,92GiB RAM (available~0,79GiB),55,99GiB диск
(available47,45GiB). Это один снимок, не подтверждение пикового запаса.
Одновременное размещение двух stacks и
мониторинга разрешается только после resource gate. Если места/памяти не
хватает, согласовать увеличение ресурсов или отдельный PROD хост; не
разворачивать второй stack с надеждой на достаточность текущего VPS.

Для текущего доступа по IP проектируем PROD на `https://135.136.178.252:8443/`,
Sandbox остаётся на существующем 443. Frontend PROD публикуется на отдельном
loopback-порту; внешний TLS обеспечивает Nginx. До применения проверить
доступность 8443, ёмкость VPS и сертификат. Cookie браузера не изолируются
портом: нужны разные имена защищённых session cookie, отдельные session stores
и проверки входа/выхода в обоих интерфейсах. Login и изменяющие запросы
проверяют точный разрешённый Origin (scheme/host/port); CORS между средами
не разрешается. CSRF проверяется внутри своей сессии. Если позднее появится домен,
можно выделить разные hostnames без изменения broker scope.

В UI постоянно видны TEST/PROD, маскированный счёт и режим доступа.
Scope `(api_slug, environment, target, account_id)` неизменяем после любого
выбора account, даже до появления фактов и у disabled подключения. Обновления
сериализуются блокировкой строки PostgreSQL; новый счёт/контур создаётся
отдельным подключением.

## Контракт доступа

1. Endpoint выбирается кодом: TEST → `sandbox-invest-public-api.tbank.ru:443`,
   PROD → `invest-public-api.tbank.ru:443`. Несовпадение environment/adapter/FQDN
   отклоняется и Core, и Worker. Произвольный FQDN запрещён.
2. Каждый процесс получает обязательный режим `BROKER_ACCESS_MODE=READ_ONLY|TRADE`.
   Отсутствующее или неверное локальное значение даёт startup ValidationError.
   Несовпадение контура/режима с Core выявляется при runtime iteration:
   итерация отказывает, ошибка логируется, затем выполняется retry. Проверка
   предшествует изменению cache, изменяющим HTTP-запросам и broker SDK actions.
   В этом этапе PROD допускается только READ_ONLY; включение стратегии явное.
3. READ_ONLY запрещает post/cancel/replace/stop-order и повторную отправку intent
   в транспортной границе независимо от решения стратегии. Разрешены чтение,
   локальная сверка/bootstrap и доставка фактов Core. Старый pending intent
   нельзя исполнять при запуске в этом режиме: остановить допуск и показать причину.
4. Первый токен PROD — брокерский read-only token. Проверяются права чтения
   выбранного счёта; отсутствие права не компенсируется автоматической сменой токена.
5. TRADE требует серверного разрешения, выбранного реального счёта, явных
   лимитов и разрешённого UID инструмента. UI подтверждает режим, но сервер
   проверяет его повторно непосредственно перед брокерской мутацией.
6. Запрет новых торговых действий должен применяться и к queued/retry intent.
   Активные заявки на бирже остаются активными: остановка приложения их не отменяет.
   Отмена при инциденте — отдельное операторское действие с аудитом.

P1/P2 реализуют выбор контура, обязательный режим, transport guards и изоляцию
конфигурации. Credential-free `BrokerScope` выдаётся отдельным internal endpoint:
реальный outbox delivery проверяет broker/account/environment и локальный cache,
включая CLOSED automation и disabled broker, без открытия broker SDK session.
Adoption UI показывает counts и диагностику; диагноз исключения не означает,
что соответствующий автомат фактически переведён в HOLD. Runtime arming,
account lease, торговые лимиты и live приёмка относятся к открытым P3/P4/P5.

## Приёмка перед торговлей

- Новое PROD состояние согласовано по external UID, количеству лотов, lot size,
  валюте и средней цене. Текущая себестоимость отделена от исторического P&L.
  Неподдерживаемые позиции, short/дробные лоты, валюты и активные stop-orders
  видны как исключения, а не исчезают из отчёта.
- Заблокированные деньги/бумаги, комиссии и торговый статус учтены по реальному
  API. Лимиты проверяются на общей нагрузке Core, Worker и мониторинга.
- READ_ONLY наблюдается минимум один полный торговый день и период закрытого
  рынка. Приложение не создаёт intent и не отправляет/отменяет заявки.
  Старые или внешние заявки могут исполняться самим брокером: это отражается
  в чтении портфеля/операций. Позиция с внешним изменением получает HOLD и
  диагноз до принятой сверки; snapshot не выдаётся за историю исполнения.
- Отказы брокера/Analytics, stale TTL, потеря ACK, restart, частичное исполнение
  и неопределённый результат отправки проверены в изолированных тестах.
- Проверены запрет второго Worker, аварийная остановка новых заявок,
  уведомление оператору, резервная копия пары PG/SQLite и восстановление
  на отдельных volumes без доступа к реальным торговым методам.
- Lease используется для обнаружения потери владельца, не как гарантия
  fencing брокера. Автоматический takeover TRADE запрещён: новый runtime
  допускается после подтверждённой остановки старого процесса/авторестарта
  и reconciliation всех unresolved intent. Пауза старого Worker после проверки
  допуска не должна позволять одновременно открыть торговлю новому.
- Численные лимиты notional/exposure/числа заявок и дневного убытка задаёт
  владелец до TRADE. Пока хоть одно обязательное значение отсутствует,
  допуск запрещён. Canary разрешает один UID, остальные позиции не торгуются.
- Ограничения продаж проверяются отдельно: max-order не должен неожиданно
  блокировать запланированный выход из позиции. Запрещённая продажа даёт
  HOLD/уведомление; автоматическая ликвидация всего счёта не предусмотрена.

## Наблюдаемость и хранение

Перед TRADE нужны статус Worker/брокера/рынка, очередь доставки, UNCERTAIN,
расхождения ledger, свежесть портфеля и действующие лимиты без SSH.
Подробности: [наблюдаемость](../../deployment/observability-plan.md),
[ёмкость и сроки хранения](../../deployment/storage-capacity.md).

Ключи дедупликации, финансовые факты и журналы восстановления не удаляются
по возрасту. Ротация технических логов не затрагивает торговый ledger.

## Переключение и откат

PROD создаётся параллельно, первоначально READ_ONLY. После принятия чтения
и всех зависимостей отдельный допуск разрешает ограниченный canary.
Расширение — отдельное решение после сверки фактических исполнений.

Откат функциональности означает запрет новых PROD мутаций и возврат к чтению.
Сначала выяснить состояние каждого отправленного/неопределённого ордера у
брокера. Не восстанавливать старую БД поверх более новых исполнений: биржевые
операции не откатываются возвратом к Sandbox. Старые releases/volumes сохраняются.
