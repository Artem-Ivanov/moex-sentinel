# Веха 0.3: жизненный цикл Core и Worker

## Цель и действующая база

Завершить пункты 0.3.1–0.3.3 дорожной карты на существующем typed runtime.
Core владеет подтверждённым состоянием; Worker предлагает изменения через
SQLite outbox и принимает авторитетные snapshots Core. Sandbox уже работает.
История прежней БД не требуется. Изменения проверяются на отдельных тестовых
хранилищах; рабочие торговые данные не используются как фикстуры.

## Переходы

Сохраняется enum `IN_QUEUE`, `OPENING`, `IN_WORK`, `HOLD`, `CLOSED`.
Общая чистая политика различает пользовательскую команду и факт Worker.

| Источник | Пользовательская команда | Предложение Worker |
| --- | --- | --- |
| IN_QUEUE | HOLD, CLOSED | OPENING, IN_WORK, HOLD, CLOSED |
| OPENING | HOLD, CLOSED | IN_WORK, HOLD, CLOSED |
| IN_WORK | HOLD, CLOSED | HOLD, CLOSED |
| HOLD | IN_QUEUE, CLOSED | IN_WORK только при валидном bootstrap |
| CLOSED | нет | нет |

Повтор идентичной локальной команды не создаёт новую ревизию или outbox-факт.
Повтор уже принятого event_id обрабатывается существующей проверкой идентичности
и возвращает прежний ACK. Новый state-факт не может обходить граф переходов.
`HOLD/BOOTSTRAPPING -> IN_WORK` сохраняет строгую атомарную группу четырёх фактов.
Обычный Worker не возобновляет пользовательский HOLD самостоятельно.

У state-факта CLOSED обязательно задан `closed_at`; у других состояний это
поле отсутствует. HOLD сохраняет фактическое исходное состояние в
`suspended_from_state` и непустую причину. Остальные состояния очищают эти поля.
Некорректные поля отклоняются до записи фактов с `INVALID_FACT_STATE`.

Правила применяются в сервисах Core и Worker, а также перед изменением
подтверждённого состояния в ingress. Хранилища защищают запись ревизией и
транзакцией. Невалидное предложение отклоняется бизнес-ошибкой без частичной записи.
Копирование авторитетного состояния Core в cache Worker является сверкой,
а не новым предложением перехода.

## Контракт и трассировка

Сохраняются существующие endpoints commands/statuses/facts и форматы payload.
Интеграционный тест связывает реальный Core HTTP app с Worker CoreClient,
локальным репозиторием и outbox: claim, активация, ACK/retry, HOLD/resume/CLOSED,
отказ запрещённого перехода и отсутствие прямого доступа Worker к Core storage.

Идентификатор hydration/reconciliation используется дальше в решении,
планировании и отправке заявки. При отсутствии hydration process_id создаётся
новый UUID. Восстановление неопределённой заявки получает отдельный стабильный
UUID по области брокера, автомату и ключу intent; все стадии этой сверки и
финализация используют его. Корреляция восстановления не требует изменения БД.
У каждой durable audit-стадии сохраняются `process_id`, `occurred_at` и `stage`.

## Границы

Не вводятся второй протокол, lease/fencing, новая стратегия или новая схема БД.
OPENING сохраняется для совместимости существующего enum. Рабочие volumes не
пересоздаются. Переключение запущенного Worker выполняется только после тестов
с учётом активных intent/outbox; итог приёмки различает код и развёртывание.

## Приёмка

Матрица переходов, регрессии Core/Worker, двухсервисный тест и корреляция стадий
должны проходить. Выполняется полная Python-регрессия с отдельным PostgreSQL,
проверки форматирования и документации. Документация отмечает 0.3 завершённой
только после проверки всего scope; следующая веха — 0.8.
