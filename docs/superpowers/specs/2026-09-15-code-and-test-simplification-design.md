# Упрощение кода и тестов: решение перед реализацией

Статус: независимое ревью пройдено; решение подготовлено для рассмотрения
пользователем, реализация не начата. См.
[план](../plans/2026-09-15-code-and-test-simplification.md) и
[отчёт ревью](../../audits/2026-09-15-simplification-plan-review.md).

## Задача и границы

Дополнить [план эксплуатации и производительности](../../deployment/refactoring-performance.md)
планом уменьшения сложности исходников и тестовой базы. Приоритет — повторяющийся
setup тестов, ясные сценарии, параметризация одинакового поведения; затем
упрощение production-кода и соблюдение границ юзкейсов.

Область анализа: четыре Python-пакета `src/`, Python-тесты `tests/`, Vue/TypeScript
в `frontend/src/`. Миграции, Docker и диагностические материалы рассматриваются
как границы совместимости, а не кандидаты на механическую перезапись.
Генерируемые контракты, зависимости, старые отчёты и данные не переписываются.

На этом этапе создаются анализ, решение, последовательность изменений и независимое
ревью. Реализация проходит отдельным следующим этапом после рассмотрения решения.
Рабочее приложение и БД для подготовки плана не изменяются.

## Варианты

| Подход | Выигрыш | Цена | Решение |
|---|---|---|---|
| Только форматирование и общий test-utils | Быстрые косметические изменения | Не устраняет смешение ответственности; общий helper может скрыть сценарии | Недостаточно |
| Поэтапное упрощение по сценариям и границам ответственности | Малые проверяемые изменения; виден источник уменьшения сложности | Нужно сопоставлять старые и новые сценарии | Рекомендуется |
| Полная перезапись слоёв и тестов одновременно | Единообразие структуры | Трудно отделить изменение поведения от рефакторинга, риск утраты регрессий | Отклонён |

## Правила тестовой базы

1. Один тест проверяет один сценарий: начальное состояние, действие, наблюдаемый
   результат. Несколько утверждений об одном результате допустимы. Цепочка
   повторной доставки — один сценарий идемпотентности, её нельзя разрезать так,
   чтобы исчезла проверка отсутствия повторного эффекта.
2. Параметризация применяется, когда совпадают действие и структура ожидаемого
   результата. Использовать `pytest.param(..., id="смысл-сценария")`; во frontend —
   именованные строки `it.each`. Ветвления `if case` внутри теста не заменяют
   отдельные сценарии. Разные побочные эффекты/границы транзакции проверяются отдельно.
3. Фикстура владеет повторяющейся подготовкой и освобождением ресурса. Фабрика
   создаёт данные с явными существенными параметрами. Arrange/Act/Assert сценария
   остаются видны в тесте. Общие assertions не должны прятать смысл результата.
4. Область по умолчанию — function. Mutable fake, Session, event loop и данные
   не становятся session-scoped ради скорости. `yield`/контекстный менеджер
   освобождает engine, client, task и файл. Root conftest не становится хранилищем
   всех фикстур; тематические фикстуры живут рядом с потребителями.
5. Повтор на разных уровнях не автоматически лишний: unit проверяет ветку
   поведения, PostgreSQL — реальные unique constraints, транзакцию и rollback,
   HTTP smoke — wiring/сериализацию. Сокращение требует таблицы: старый сценарий →
   новый тест/параметр → сохраняемый контракт → обоснование удаления дубля.
6. Не ставить цель уменьшить число collected cases. Параметризация уменьшает код,
   сохраняя либо улучшая различимость сценариев. Измерять объём повторяющегося
   setup, понятность теста, набор сценариев и время выполнения на одинаковой среде.
7. При чистом рефакторинге сначала запустить существующие целевые тесты, затем
   изменить структуру и запустить их снова. Новые тесты нужны для обнаруженного
   пробела поведения, а не для каждого перемещения функции.
8. Перемещение тестов между пакетами и изменение сценариев — разные проверяемые
   шаги. Сначала сохранить входы, assertions, порядок действий и replay 1:1,
   затем извлекать setup и параметризовать с отдельной картой соответствия.
9. Общие helpers подчиняются ADR [0004](../../decisions/0004-shared-application-primitives.md):
   три реальных потребителя с одинаковой семантикой либо обоснованное исключение
   для контракта/инварианта/ресурсной изоляции. Локальная фабрика не требует
   преждевременного переноса в общий пакет.

## Правила production-кода

### Юзкейсы и ответственность

Следовать ADR [0005](../../decisions/0005-application-layering-pattern.md):
транспорт или runtime-актор вызывает конечный юзкейс; юзкейс координирует сервисы;
сервисы реализуют правила и работают через порты; адаптеры реализуют I/O.
Юзкейс не вызывает другой юзкейс. Бесконечный loop, supervision, transport DTO,
математическая функция и repository не превращаются в юзкейсы.

Проверять реальные входы сценариев, а не суффикс имени класса. Существующий
координатор конечной операции можно перенести/переименовать в юзкейс; не добавлять
пустой класс поверх каждой стадии. Если lifecycle и операция смешаны, отделить
только конечную операцию. Общая транзакция остаётся общей: перенос кода между
классами не создаёт дополнительных commit и не расширяет lock scope.

Для frontend применять разделение отображения, прикладного действия и API-клиента
там, где оно уменьшает дублирование. Не переносить Python-иерархию классов в Vue
механически. Чистые преобразования могут оставаться функциями, ресурсный lifecycle —
composable, сетевой транспорт — API-модулем.

### Пустота, ошибки и сложность

Каждую удаляемую проверку подтвердить контрактом: вход валидируется во всех
производственных путях, тип не Optional, после проверки нет конкурентного
изменения, старые persisted payload не обходят эту границу. Если подтверждения
нет, проверка остаётся либо переносится к единственному владельцу валидации.

Отсутствие котировки, заявки, истории, baseline или настройки может быть нормальным
состоянием. `None`, пустая строка, ноль и пустая коллекция не взаимозаменяемы.
Не заменять их общей truthiness-проверкой, `assert` или значением по умолчанию.
Проверки на внешнем вводе, границе хранения, freshness, status/revision/sequence
сохраняются. Удаляются доказанные повторные проверки и невозможные fallback-ветки.

Предпочитать ранний выход, именованный промежуточный результат и прямой цикл
сложным вложенным выражениям. Ошибки преобразуются по конкретным типам на границах;
не вводить универсальный error mapper. Не объединять разные retry-политики
брокера, outbox и market data только из-за похожего синтаксиса.

### Классы и docstrings

Класс оправдан состоянием, lifecycle, внедряемыми зависимостями или контрактом
прикладного сценария. Чистая функция без этих свойств не требует класса-сервиса.
Новый port появляется для фактического потребителя/изоляции инфраструктуры,
а не для зеркального копирования всех методов реализации.

Документировать функции и методы при проходе по подсистеме: назначение, входные
единицы, результат, значимые ошибки, побочные эффекты, владение ресурсом или
транзакцией. Для простых функций достаточно одной содержательной строки.
Контракт Protocol документируется у владельца; реализация уточняет отличия,
а не копирует длинный текст. Не заменять понятные имена docstring-пересказом кода.
Пропуски отслеживать по подсистемам; сгенерированные файлы и механические accessors
можно исключить явно с обоснованием. Новое глобальное lint-правило не должно
создать тысячи бессодержательных комментариев за один проход.

## Неприкосновенные контракты

- Внешние HTTP/typed-fact payload, status/error/reason codes и broker IDs.
- Один активный Worker на scope; отсутствие повторного broker submit при UNCERTAIN.
- Атомарность intent/execution/lot/outbox и bootstrap quartet; replay/ACK и порядок sequence.
- LIFO, частичные комиссии, valuation по authoritative lots; поздние исполнения.
- Millisecond precision на persisted facts; исходная точность котировки для freshness.
- HOLD не превращается в разрешение торговли; retry reconciliation не отправляет BUY повторно.
- Отсутствие baseline и закрытый рынок остаются явно моделируемыми состояниями.
- Миграции, существующие volumes и данные не меняются в рамках структурного рефакторинга.

## Критерий готовности решения и реализации

Решение готово после независимого ревью двух аудитов и объединённого плана:
конкретные файлы, сценарии, этапы, зависимости, проверки и ограничения указаны;
существенные замечания закрыты. Это не означает, что реализация уже выполнена.

Каждая будущая веха имеет автора и другого рецензента, таблицу сохранённых
сценариев, целевые успешные проверки и небольшой проверяемый diff. Полный backend
прогон использует отдельную PostgreSQL; frontend проверяется Vitest и typecheck/build
при изменении соответствующего кода. Skip PostgreSQL не считается успешной проверкой БД.
Показатель уменьшения строк — дополнительный, сохранение поведения обязательно.
