# Авторизация одного оператора перед удалённым доступом

Статус: схема согласована с пользователем 01.10.2026; спецификация ожидает
проверки пользователем. Продуктовая реализация не начата.

## Цель и границы

Один оператор входит в браузерный интерфейс по имени пользователя и паролю.
Прямой запрос к пользовательскому API без действующей сессии не получает
позиции, брокерские настройки, токен или возможность изменить торговлю.
Учётная запись задаётся на сервере; регистрации, нескольких ролей, сброса
пароля через UI и миграции Core PostgreSQL в этой задаче нет. Эта работа
готовит приложение к доступу по `https://IP`, но не выпускает его в интернет:
TLS, сетевой экран и серверный деплой остаются отдельными шагами.

## Выбранный подход

| Подход | Свойства | Решение |
| --- | --- | --- |
| Серверная сессия в защищённой cookie | Страница входа, восстановление входа после обновления страницы, настоящий выход | Выбран пользователем |
| HTTP Basic на каждом запросе | Меньше кода, но браузерный выход и собственная форма входа неудобны | Не выбран |
| Токен в `localStorage` | Простой frontend, но доступен JavaScript при XSS | Не выбран |

Frontend показывает форму входа и скрывает маршруты до проверки сессии.
Backend остаётся единственным источником решения о доступе: проверка маршрута
на фронтенде не даёт прав на `/api`. Текущий один процесс Uvicorn хранит
сессии в памяти. Перезапуск Core завершает все сессии; добавление второго
процесса потребует общего хранилища сессий до масштабирования.

## Учётные данные и запуск

- В окружении backend обязательны `AUTH_USERNAME` и `AUTH_PASSWORD_HASH`.
  Значение второго поля — `scrypt:16384:8:5:<32 hex соли>:<64 hex digest>`.
  Исходный пароль и готовая сессия не хранятся в Git, Compose, БД или browser
  storage. Оператор создаёт хеш командой CLI с вводом пароля без эха;
  команда печатает только хеш. Для scrypt используются
  `N=2^14, r=8, p=5`, случайная соль 16 байт и digest 32 байта. CLI
  требует пароль длиной от 16 до 1024 байт в UTF-8; имя — от 1 до 64 символов
  без переводов строки.
- По умолчанию cookie требует HTTPS. Существующий локальный интерфейс
  `http://127.0.0.1:8080` может явно включить `AUTH_INSECURE_LOOPBACK=true`:
  только запросы с Host `127.0.0.1` или `localhost` получают отдельную cookie
  `moex-local-session` без `Secure` и без префикса `__Host-`. Логин, срок,
  `HttpOnly`, `SameSite=Strict` и CSRF остаются обязательными. Remote Compose
  жёстко задаёт `AUTH_INSECURE_LOOPBACK=false`, а preflight отклоняет иной
  результат. При реализации `frontend/package.json` меняет штатную команду
  `npm run dev` на `vite --host 127.0.0.1`. Прямой запуск backend для
  разработки выполняется командой Uvicorn с `--host 127.0.0.1`, а контейнерный
  entrypoint с `0.0.0.0` используется только без опубликованного backend-порта.
  Локальный frontend и прямой backend должны быть привязаны к loopback:
  проверка Host сама по себе не подтверждает локальность TCP-соединения.
  Backend в secure режиме не принимает локальную cookie.
- Backend проверяет формат и наличие настроек при старте и не запускает
  пользовательский API при ошибке. Production entrypoint не имеет настройки,
  которая открывает `/api` без авторизации. Тесты старых бизнес-сценариев
  могут передать явную test-only замену проверки в `create_app`; отдельные
  тесты авторизации проходят через настоящую проверку.
- Имя пользователя сравнивается точно, без изменения регистра. Неверное имя
  или пароль дают одинаковый ответ `401` без раскрытия причины; проверка
  scrypt выполняется и при неверном имени. Сравнение verifier выполняется
  через `hmac.compare_digest`. Пароль и заголовки cookie/CSRF не попадают
  в логи. Длина входов ограничена, чтобы дорогая проверка пароля не стала
  неограниченным расходом ресурсов.
- Backend ограничивает одновременные проверки scrypt двумя задачами; при
  исчерпании слотов отвечает `429` с `Retry-After: 1`, не блокируя
  учётную запись по чужим неудачным попыткам. На публичном reverse proxy
  `/api/auth/login` ограничивается по исходному IP клиента до 10 запросов
  в минуту с burst до 5 запросов. Backend не доверяет клиентскому
  `X-Forwarded-For` без настройки доверенного proxy. Ответ `429` не раскрывает
  существование пользователя. scrypt выполняется вне event loop в ограниченном
  пуле, чтобы проверка пароля не задерживала health и другие запросы.
  Ограничение edge входит в приёмку деплоя.

## HTTP-контракт и сессии

| Маршрут | Контракт |
| --- | --- |
| `POST /api/auth/login` | JSON `username`, `password`; при успехе выдаёт новую сессию и объект `{username, csrf_token}`; при ошибке `401` или `429` |
| `GET /api/auth/session` | Для действующей cookie возвращает `{username, csrf_token}`, иначе `401` |
| `POST /api/auth/logout` | Требует сессию и CSRF, удаляет сессию на сервере и cookie; ответ `204` |
| `GET /api/health` | Остаётся доступным без сессии для Docker readiness; не возвращает секреты |
| Остальные `/api/*` | Требуют сессию; изменяющие методы дополнительно требуют `X-CSRF-Token` |

Сессия получает случайный идентификатор минимум 256 бит и отдельный случайный
CSRF-токен. Сервер хранит только хеш идентификатора, имя оператора, CSRF-токен
и срок действия по монотонным часам процесса. Срок — 12 часов с момента
входа, без автоматического продления. Просроченные записи очищаются; выход
отзывает запись немедленно. В secure режиме cookie `__Host-moex-session`
имеет `Secure`, `HttpOnly`, `SameSite=Strict`,
`Path=/`, без `Domain`, с `Max-Age` не длиннее серверного срока. Браузер не
читает идентификатор сессии. Ответы входа, проверки сессии и защищённого API
получают `Cache-Control: no-store`.

Для `POST`, `PUT`, `PATCH`, `DELETE` пользовательских маршрутов backend
сравнивает заголовок `X-CSRF-Token` с токеном сессии постоянным по времени
способом; отсутствие или несовпадение дают `403` без выполнения операции.
Вход не требует сессии/CSRF. Приложение не включает CORS для чужих origins.
Все браузерные вызовы остаются same-origin через frontend Nginx.

Маршруты `/internal/*` Worker и Analytics остаются отдельными контрактами
без операторской cookie: эти сервисы не получают логин и пароль. Remote
Compose не публикует backend, а frontend Nginx проксирует только `/api/`.
Наружный reverse proxy обязан закрывать `/internal/*` и отдавать только
frontend. Авторизация сервисов внутри Docker-сети и защита хоста от
недоверенных контейнеров — отдельная задача, если такая граница доверия
появится.

## Поведение интерфейса

- При открытии frontend запрашивает `/api/auth/session`; до ответа не
  отображает данные и торговые действия. `401` ведёт на `/login` с сохранением
  только внутреннего маршрута для возврата после входа; внешние URL не
  принимаются как адрес перенаправления.
- Форма входа отправляет имя и пароль только на same-origin `/api/auth/login`.
  Пароль остаётся в памяти формы до ответа и не сохраняется в браузерном
  хранилище. Ошибки показываются без уточнения, какая часть пары неверна.
- После входа frontend хранит в памяти только объект сессии и CSRF-токен.
  Общий API-клиент добавляет `X-CSRF-Token` к изменяющим запросам. После
  обновления страницы состояние восстанавливается через `/api/auth/session`.
- Кнопка «Выйти» вызывает `/api/auth/logout`, очищает локальное состояние и
  переводит на `/login`. Любой `401` защищённого API также сбрасывает
  локальное состояние. Ошибка сети не трактуется как неверный пароль.

## Проверки и критерии готовности

1. Backend-тесты проверяют успешный и неуспешный вход, отсутствие утечки
   verifier, атрибуты cookie, отказ прямому `/api` без сессии, CSRF на
   изменяющем маршруте, отзыв после выхода, истечение срока, лимит входа,
   доступность health и сохранение внутренних контрактов.
2. Frontend-тесты проверяют форму, ожидание проверки сессии, guard маршрутов,
   восстановление после reload, добавление CSRF, выход и переход на вход при
   `401`. Существующие тесты бизнес-потоков остаются зелёными.
3. Контракт Compose проверяет, что backend получает обязательные параметры,
   локальный HTTP требует явного loopback-флага и штатный Vite dev слушает
   только loopback, а remote preflight не
   допускает этот флаг или пустой/примерный verifier. Проверки не печатают
   пароль, verifier или cookie.
4. На тестовом HTTPS окружении проверяются реальные cookie и `401/403` для
   анонимного/CSRF запроса, `200` после входа, `401` после выхода. Затем
   проводится независимое кросс-ревью кода, безопасности границ и тестов.

Локальная браузерная проверка проводится по `http://127.0.0.1:8080` только
с явным loopback-флагом; тесты проверяют отказ этого режима для другого Host.
Удалённая браузерная проверка проводится только через HTTPS, с `Secure`
cookie. Исключение браузеров для `localhost` не считается защитой или
критерием приёмки.
