## PT1/PT2

Known TEST/PROD TRADE допускают существующие команды UI; READ_ONLY/loading/unknown закрыты. Возможность команды не означает разрешение счёта на broker writes.

Risk mark получает только свежий стакан unary GetOrderBook: exact instrument UID, настоящий aware `orderbook_ts`, возраст 0..1с при окончании capture и существующих consumers. Обе стороны непустые, цены finite/positive, quantity strict int>0, best bid<best ask. Best ask=min(valid asks), best bid=max(valid bids). Для LONG exposure используется ask; это консервативная оценка единицы, не обещание ликвидности всего объёма. Невалидный/старый/будущий/пустой/перекрещенный стакан закрывает риск; LastPrice fallback и подмена timestamp временем ответа отсутствуют. Existing permit1с, RTT deduction, final clock после locks, ownership и reservations сохраняются.

## PT3: ежедневная подготовка

`DAILY_ADMISSION_PREPARATION_ENABLED=false` по умолчанию. Scope — только явно заданный существующий `INTERNAL_WORKER_BROKER_ID`, active/unarchived PROD с действующим owner/generation/lease. READ_ONLY, TEST, missing scope/owner или просроченный lease пропускаются с причиной. Подготовка не регистрирует кандидата, не передаёт owner и не снимает HOLD/revoke.

Core запускает один `DailyAdmissionPreparationService`: `prepare_once()`, `run()`, `snapshot()`. Первая попытка при старте, затем проверка нового московского дня не реже 60с; ошибке — backoff60/120/300с. Синхронные DB операции выполняются через `bind_sync_runner(executor.run)`, async SDK остаётся в event loop; попытка ограничена по времени, cancellation выходит наружу. Lifespan отменяет и await фоновые задачи до закрытия executor/HTTP/engine.

Если база текущего дня уже принята, вернуть её без повторного SDK capture, событий, revision++, очистки limits/ARM. Иначе authoritative account-only snapshot и `ensure_daily_baseline`: lock брокера/admission, final clock после locks проверяет день MSK, валидность snapshot и текущие scope/config/owner/gen, unique(broker,day) разрешает двух исполнителей. Повтор automatic возвращает победившую immutable baseline; ручной POST сохраняет прежний 409. Midnight/expiry/смена owner/config под lock закрывают попытку и требуют свежего чтения. Никакого сброса дневного убытка. Поздняя первая принятая RUB equity не считается P&L от полуночи.

Уточнение STOP policy root14.10: новый день допускает baseline при живом owner даже в STOP_REQUIRED/recovery_only. Удаляются только вчерашние ARM/caps, STOP_REQUIRED и recovery flags сохраняются. Same-day повтор полностью неизменен. Автоматический CANARY reconcile в STOP/recovery пропускается: RECOVERY_REQUIRED требует явной операторской сверки; daily preparation не выполняет recovery и не отменяет revoke.

`DAILY_ADMISSION_CANARY_UID=""` — только baseline. Непустой UID явно задаёт read-only CANARY preparation. Применяются существующие reconciliation gates. Автоматическая успешная сверка возможна только для неактивированного допуска; повтор того же day/owner/gen/config не выполняет её снова. Ни один периодический вызов не очищает ARMED/limits. Неуспешный автоматический snapshot не создаёт новую failed reconciliation запись каждый tick: safe reason в observation и backoff. Явный operator reconcile сохраняет прежний контракт. Срок successful reconciliation остаётся min(capture+30с, lease); после истечения перед ARM требуется новая явная сверка.

Suggested limits — preview, без записи admission.limits: max order=free RUB−blocked cash; exposure=equity; outstanding=count positive noncurrency positions; dayloss=accepted baseline equity×0.05. Невалидные/нулевые входы дают reason и отсутствие пригодных caps; existing reservation/commission submit guards неизменны. ARM всегда явный. Автоматическое продление ARM не входит в scope.

Authenticated read-only GET `/api/brokers/{broker_id}/trading-admission/preparation` возвращает последний observation указанного scope: day, captured_at, status(DISABLED/WAITING/BASELINE_ACCEPTED/PREPARED/BLOCKED), safe reason, baseline_id, owner_id/gen, config fingerprint, reconciliation_id/valid_until, suggested_limits, risk reasons. Не возвращать SDK bodies/account identifiers/secrets. Нет observation после рестарта — UNKNOWN/WAITING, неверный scope404. Перед выдачей проверяются текущие day/owner/config/lease и срок; старый observation не показывает готовность. Fingerprint сравнивается с текущим вычисленным конфигом, а не с nullable armed fingerprint. GET ничего не подготавливает и не мутирует.

Замороженные HTTP поля: `moscow_day`, `captured_at`, `status`, nullable `reason`, `baseline_id`, `owner_runtime_instance_id`, `owner_generation`, `configuration_fingerprint`, `reconciliation_id`, `reconciliation_valid_until`, `suggested_limits`, `risk_reasons`. Suggested limits имеют существующую форму AdmissionLimits и являются preview. Fixed reasons: DAILY_PREPARATION_DISABLED, NOT_OBSERVED, SCOPE_UNAVAILABLE, OWNER_MISSING, OWNER_MISMATCH, LEASE_EXPIRED, BASELINE_REQUIRED, SNAPSHOT_INVALID, SNAPSHOT_EXPIRED, MOSCOW_DAY_CHANGED, CONFIGURATION_CHANGED, RECONCILIATION_REQUIRED, RECONCILIATION_EXPIRED, RECOVERY_REQUIRED, ARM_REQUIRED, RISK_DATA_UNKNOWN, CORE_UNAVAILABLE. `PREPARED` только при свежей CANARY can_arm, reason ARM_REQUIRED: это готовность к явному ARM, не торговля. Baseline-only — BASELINE_ACCEPTED/RECONCILIATION_REQUIRED. UUID/UTC-ms/fingerprint следуют существующим admission primitives.

## PT4: диагностика и Telegram

Worker `prepare`: чужой/невалидный owner→NOT_OWNER; совпавший owner+recovery_only→STOP_REQUIRED. WAIT/no intent сохраняются. UI раздельно показывает HOLD/resume_pending позиции и admission счёта, московскую дату baseline, owner/lease, limits, reconciliation/ARM и свежесть preparation. Никаких автоматических control POST. При смене broker/ошибке/устаревшем ответе нельзя оставлять чужую зелёную готовность.

`TradingReadinessAlertService` получает callback безопасных domain observations, без чтения Worker SQLite или брокерских SDK mutations. Core integration принадлежит Core автору, alert implementation — отдельному автору. Сигналы: STOP_REQUIRED, потеря heartbeat UNKNOWN, CONTROL_STALLED/error progress, outbox FAILED/OLD_PENDING/UNKNOWN, утрата подтверждённой readiness/ошибка preparation. ARM_REQUIRED сам по себе не critical. Heartbeat TTL30с+confirmation30с, progress stall30с, pending age60с+confirmation60с; FAILED/STOP_REQUIRED после первого подтверждённого наблюдения, startup UNKNOWN grace60с. RECOVERED относится к конкретному сигналу, не означает возобновление торговли.

Core-facing frozen `ReadinessObservation`: captured_at, existing WorkerObservation, account_status(DISARMED/ARMED/STOP_REQUIRED/UNKNOWN), account_effective_can_submit(bool или None при unknown), recovery_only, preparation_status(READY/PENDING/FAILED/UNKNOWN), preparation_reason(READY/OWNER_MISSING/OWNER_MISMATCH/LEASE_EXPIRED/BASELINE_MISSING/RECONCILIATION_REQUIRED/ARM_REQUIRED/MARKET_STALE/CORE_UNAVAILABLE/NOT_OBSERVED/UNKNOWN). `TradingReadinessAlertService(observe async callback, transport|None, *, environment, enabled, clock, monotonic_clock)` имеет async `observe_once`, `run`, `close`. Core владеет run task, отменяет и await его перед resource cleanup; service не создаёт дочерних delivery tasks. Disabled не вызывает observer/transport. Factory `create_telegram_alert_transport(*, bot_token:SecretStr, chat_id:str, run_sync:executor.run)` возвращает async `send_message(text)`; ошибки только фиксированные TIMEOUT/HTTP_ERROR/NETWORK_ERROR/INVALID_RESPONSE/RESPONSE_TOO_LARGE. Preparation READY не означает account effective_can_submit. READINESS_LOST определяется confirmed effective=False при ARMED или после ранее observed effective=True; истечение preparation/reconciliation для нового ARM само по себе не означает потерю действующего допуска. Safe reason проверяется runtime allowlist перед rendering, unknown→UNKNOWN.

Telegram optional/disabled по умолчанию. Минимальная конфигурация `TELEGRAM_ALERTS_ENABLED=false`, `TELEGRAM_BOT_TOKEN` как SecretStr и `TELEGRAM_CHAT_ID`. Enabled без валидной конфигурации — явная ошибка настроек; partial disabled config не включает отправки. Credentials не попадают в docs/API/logs. Sender использует фиксированный HTTPS api.telegram.org и sendMessage, TLS verify, timeout≤5с, без environment proxy/redirect. Token находится в URL path: исключить request URL logging; предпочтительно stdlib urllib opener с отключённым proxy и запрещённым redirect через executor, без новой зависимости. Exceptions преобразуются в фиксированные безопасные error codes; не log raw URL/body/HTTPError/traceback. Payload содержит env/time/severity/signal/safe reason/incidentID, без accountID/equity/истории/SDK exception text. Ответ читается с фиксированным лимитом размера; success только при JSON `ok is True`, небезопасные description/body не выводятся. Формат подтверждён [официальным Bot API](https://core.telegram.org/bots/api#sendmessage) 14.10. Tests mock transport, ни одного настоящего send.

Incident dedup по fixed scope+signal, уведомление при входе/material safe reason change и восстановлении. Queue bounded max16/coalesced; retry30/60/300с, failed delivery не считается delivered. Никакого влияния ошибки Telegram на admission/Worker. После рестарта допускается одно повторное сообщение текущего инцидента; durable exactly-once не требуется и migration не добавляется. Внутренний Core sender не обнаруживает смерть всего VPS/Core: внешний uptime probe и подтверждённый Telegram recipient/test delivery остаются операционной приёмкой после merge/deploy.
