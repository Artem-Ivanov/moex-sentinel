# Торговля по IN_WORK и общим лимитам счёта

## Подтверждённое требование

16.10 пользователь потребовал удалить лишние торговые допуски и явно подтвердил:
«Да, IN_WORK достаточно; убрать отдельные ручные допуски». При включённом PROD
TRADE любой автомат счёта в IN_WORK может создать конкретную допустимую заявку,
если она удовлетворяет биржевым условиям и общим финансовым лимитам. Отдельный
выбор GOLD/canary UID, ежедневный ARM, срок ARM до полуночи и ручное подтверждение
recovery/reconciliation перестают быть условиями торговли. Это заменяет прежнее
решение отложить multi-UID/auto ARM; новый пользовательский сценарий не содержит
скрытого автоматического вызова прежнего ARM.

## Границы исполнения

Core владеет PostgreSQL, финансовыми лимитами, актуальным риск-контролем и
атомарными резервами. Worker владеет SQLite/outbox и один вызывает торговый SDK.
Analytics остаётся market-only. HOLD, CLOSED, отключённый broker/READ_ONLY и
выключенная стратегия не разрешают новую отправку. Auth, account/config binding,
единственный owner/generation, постоянный idempotency key, UNKNOWN-резервы и
подтверждённые факты сохраняются как условия корректного исполнения конкретной
заявки. Они не требуют нового ручного согласования каждой позиции или дня.
Контролируемая передача owner при deployment сохраняется; после корректной
передачи нет отдельного ручного снятия recovery-only.

## Единый контракт и хранение лимитов

`AdmissionLimits` канонически содержит currency=RUB, exposure_scope=ACCOUNT_GROSS
и ровно четыре положительных лимита: max_order_notional, max_exposure,
max_outstanding_orders, max_daily_loss. Прежний JSON с canary_uid и
CANARY_UID_GROSS читается совместимо: UID не ограничивает торговлю, scope
нормализуется к ACCOUNT_GROSS, числовые значения не меняются. Новые записи
каноничны; legacy ARM/reconciliation metadata в истории сохраняется и не
используется как бизнес-допуск. Нельзя изобретать денежные defaults или
пересчитывать сохранённые caps при renewal/restart/смене даты.

Отдельный operator-authenticated `PUT /api/brokers/{broker_id}/trading-admission/limits`
принимает `UpdateLimitsRequest(expected_revision, limits)` и возвращает свежий
`AdmissionView`. Optimistic revision/account scope/CSRF обязательны; запись caps
не вызывает брокерских операций. UI редактирует четыре caps на уровне счёта и
подтверждает сохранение только после ответа Core. Старые ARM endpoints не
должны оставаться обязательным или скрытым шагом нового пути. Совместимые
служебные API могут сохраняться для истории/диагностики; явная emergency revoke
должна выражать остановку автоматов через HOLD, а не создавать sticky gate,
требующий отдельного ARM для уже включённых IN_WORK автоматов. Reconcile и
новая baseline не очищают caps.

`AdmissionView.effective_can_submit` выражает текущую техническую готовность
счёта с заданными caps. Отсутствие ARM, canary, истёкшая operator reconciliation
и legacy recovery_only не добавляют denial. Существующие ARM/recovery поля
могут оставаться историческими/совместимыми nullable полями, но UI не выводит
их как требование к пользователю. Конкретный IN_WORK и instrument binding
перепроверяются Core под тем же lock, что выдача резерва, включая HOLD-race.

## Общий риск по нескольким инструментам

Экспозиция — сумма положительных RUB позиций счёта по свежим mark, плюс
неисполненная часть BUY-резервов по всем UID, плюс новая BUY по консервативной
оценке max(limit notional, fresh mark notional). SELL не уменьшает расчётную
экспозицию до подтверждённого исполнения. SELL проверяет позицию своего UID;
денежные резервы BUY и число незавершённых заявок учитываются по всему счёту.
Четыре прежних числовых caps сохраняются; scope max_exposure становится общим.

Каждый положительный holding и активная reservation UID имеют собственные
lot_size, currency, свежий mark и время mark. Пропущенные/дублированные/
неоценённые позиции, unsupported instrument/currency, неатрибутированные broker
orders или UNKNOWN не пропускаются как нулевой риск. Свежие оценки положительных
holdings и активных заявок получаются read-only SDK с ограниченной конкурентностью
и без долгоживущего кэша риска. Подтверждённый нулевой UID из SETTLED history может
переносить свой прежний per-UID lot anchor в новый ACCOUNT_ONLY snapshot без новой
котировки. Если нулевой quantity или lot нельзя доказать, admission закрывается.
Параметры запрошенной заявки соответствуют каталожным инструменту/лоту/tick/API
trade availability.

Автоматическая внутренняя сверка использует per-UID anchors и lot_size каждой
резервации. Scalar canary anchor нельзя применять к другому UID. Совместимые
additive anchors хранятся в существующем reconciliation JSON; старые scalar
записи читаются как исторические только для своего UID. Bootstrap account anchor
разрешён по полному свежему snapshot при доказанно согласованных/отсутствующих
незавершённых резервах; неизвестные состояния не обнуляются. Дельты fills
учитываются ровно один раз, отдельно по UID; окончательная запись резервов
перепроверяет owner/revision/automation IN_WORK/reservation digest под lock.
При гонке/несовпадении quantities исход — объяснимый отказ, без новой отправки.
Сверка выполняется внутри обычного риск-пути и не является ручным разрешением.

## Смена дня и restart

Daily loss считается относительно первого принятого equity snapshot текущего
московского дня с существующей коррекцией внешних денежных потоков. Baseline
создаётся автоматически и идемпотентно: scheduler заранее либо on-demand перед
первой конкретной заявкой, если scheduler ещё не успел. Неизвестные equity или
операции закрывают риск-проверку до успешного автоматического чтения. Нельзя
подменять их нулём. Новый день не стирает caps, не ставит HOLD/recovery/STOP и не
требует нового ARM; прежний принятый snapshot дня неизменен. Restart/owner transfer
также сохраняет caps и permanent consumed keys; неопределённые прежние заявки
сначала восстанавливаются штатно, без повторного SDK POST.

## Исполнимый permit и причины отказа

Точная заявка по-прежнему получает атомарный bound submit permit после риска.
Это автоматическое подтверждение лимитов конкретной заявки, не отдельный
пользовательский доступ. Рыночная свежесть/секундные risk и permit бюджеты не
увеличиваются, stale заявка не отправляется. Сигнал, созданный по истёкшему
рынку, пересчитывается обычным циклом, а не переотправляется с тем же ключом.

Устранить двойное списание времени Core risk/DB из срока уже выданного permit:
добавить optional `server_processing_ms` (целое >=0, default0 для прежнего ответа)
в SubmitPermit. Core измеряет собственную длительность до сериализации ответа
монотонными часами и округляет вниз до миллисекунд. Worker консервативно вычитает
из оставшегося server permit только transport budget = max(0, measured HTTP RTT
− server_processing_ms), сохраняя локальные market/deadline ограничения и все
bindings. Значение processing больше полного наблюдённого RTT не считается
доказанным сокращением транспорта: используется прежний полный RTT, с безопасным
reason/diagnostics. Прошлое processing никогда не увеличивает server expiry.
Тесты доказывают свежий permit после долгого server processing и отсутствие SDK
post при реально истёкшем рынке/permit, некорректной metadata/сдвиге часов.

Definitive SubmitDenied.reason и typed pre-RPC abort reason сохраняются безопасным
enum в business audit, вместе с длительностями/остатком permit. Не выводить
credentials/raw SDK exception text. Неопределённый исход сохраняет UNKNOWN и
резерв; никакой blind retry/освобождения по одному отсутствующему broker ID.

## Совместимость и выпуск

DDL по текущему аудиту не требуется: лимиты/anchors уже JSON, scalar nullable.
Любое фактически добавленное DDL потребует migration+guarded downgrade и проверки
на отдельной тестовой БД. Финансовые facts/history/reservations/volumes не удалять.
Совместимость чтения прежнего JSON проверяется тестом. После канонической записи
ACCOUNT_GROSS прежний single-UID release не считать совместимым fallback:
откатывать приложение можно только на сборку, понимающую новый контракт, с
сохранением схемы/данных. Core/Worker/frontend выпускаются согласованно.

В этой задаче реализуется и проверяется локальный checkout. Новых веток/worktree,
stage/commit/push нет; исходные ENV доработки и PNG сохраняются. SSH/изменения
VPS/реальные заявки/Telegram не включаются автоматически в coding-задачу.

## Приёмка

- Два разных IN_WORK UID с разными lot_size проходят без canary/ARM/reconcile;
  HOLD/READ_ONLY/wrong scope/owner/UNKNOWN/duplicate по-прежнему не вызывают POST.
- Сумма позиций и BUY резервов всех UID ограничена общим cap; partial fills,
  sellable units и восстановление считаются своим lot_size без двойного учёта.
- Caps сохраняются при смене дня/перезапуске/передаче owner; baseline появляется
  автоматически ровно один раз, без ручного подтверждения.
- Optimistic caps edit/CSRF/account isolation и HOLD-before-grant race проверены.
- Реальный bounded permit пригоден после медленного Core processing, stale,
  malformed и uncertain paths остаются fail-closed; deny причина видима в аудите.
- UI содержит IN_WORK/HOLD и четыре общих cap, без manual ARM/canary/reconcile
  prerequisites. Targeted Python/PG/frontend и общие релевантные проверки PASS.
- Независимый cross-review всех пакетов и интеграции: C/I исправлены и повторно
  проверены; исторический runtime не выдаётся за обновлённый.
