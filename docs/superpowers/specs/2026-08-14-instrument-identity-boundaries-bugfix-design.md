# Границы идентификаторов инструмента

## Проблема

Каталог хранит два идентификатора: внутренний `id` записи и внешний брокерский `instrument_id`. Список инструментов отдаёт оба, но frontend передаёт внешний идентификатор в API карточки и отбора, где repository ожидает внутренний. Поэтому карточка отвечает `INSTRUMENT_NOT_FOUND`.

Операции брокера, напротив, содержат внешний идентификатор. Обогащение тикером ошибочно вызывает поиск каталога по внутреннему `id`, скрывает исключение и возвращает `ticker: null`.

## Контракт

- Внутренний `id` используется API каталога, отбором инструмента и созданием автомата.
- Внешний `instrument_id` используется только во взаимодействии с брокером: свечи, позиции и операции.
- Карточка загружается по внутреннему `id`, после чего внешний идентификатор берётся из ответа карточки для загрузки свечей.
- Repository предоставляет отдельный scoped-поиск по внешнему идентификатору для обогащения брокерских данных.
- Отсутствие записи при обогащении является штатным случаем и не скрывается через широкий `except Exception`.

## Изменения

Frontend списка передаёт `item.id` в route карточки и endpoint отбора. Страница карточки использует route-параметр для catalog details и создания автомата, а `data.instrument.instrument_id` — для свечей.

Backend добавляет `find_by_external_instrument_id(user_broker_id, external_instrument_id)`. Сервис портфеля использует этот метод для заполнения тикера операции. Существующий `get()` сохраняет строгую семантику поиска по внутреннему ключу.

## Проверки

- route карточки получает внутренний `id`, когда оба идентификатора различаются;
- отбор отправляет внутренний `id`;
- карточка запрашивается по внутреннему `id`, свечи — по внешнему;
- repository не смешивает одинаковый внешний UID разных broker scopes;
- операция с внешним UID получает тикер из каталога;
- отсутствие каталожной записи оставляет nullable ticker без подавления программных ошибок.
