# Веха 0.9.6: сокращение повторных чтений Core

- **Статус:** [x] Завершена 2026-09-09: [приёмка, измерения и обновление Compose](milestone-0.9.6-acceptance-2026-09-09.md).
- **Основание:** [профиль PostgreSQL 0.9.4](milestone-0.9.4-acceptance-2026-09-09.md).
- **Цель:** сократить лишние SQL-обращения при приёме фактов, сохранив существующий контракт.

## Подтверждённая проблема

В исходном последовательном WAIT-профиле 6/20/50 инструментов Core выполнял
111/112/115 SQL-вызовов на решение; SQL cursor execution занимает 65–70%
ingress. После успешного CAS UPDATE методы `accept_supporting_fact` и
`accept_state_fact` возвращали id и выполняли отдельный `get` того же автомата.
Это проверено исходным кодом, независимо от гипотез о внешней песочнице.

## Первый объём

1. Вернуть актуальное состояние автомата из самого UPDATE RETURNING и убрать
   последующий SELECT на успешном пути. Не менять revision/sequence предикаты,
   семантику повторной доставки или порядок сохранения фактов.
2. Сохранить различение NOT_FOUND, REVISION_CONFLICT и SEQUENCE_CONFLICT на
   неуспешном CAS, возвращаемый DTO, точность UTC и значения полей lifecycle.
   Учесть SQLAlchemy identity map: уже загруженная ORM-сущность не должна дать
   устаревшее состояние после UPDATE.
3. Проверить supporting/state fact на SQLite и отдельной PostgreSQL, включая
   последовательные обновления в одном UoW, rollback группы, конкурирующие
   revision/sequence и exact replay. Нельзя заменять контракт проверкой SQL-строки.
4. Повторить неизменный профиль 6/20/50, batch=100, warmup=3, iterations=100.
   Сравнить SQL count, p50/p95/p99, throughput и условия с baseline 0.9.4.
   Проверяемый минимальный эффект — отсутствие дополнительного SELECT автомата
   после каждого успешного accept. Улучшение latency подтверждать измерением.
5. Пройти независимое кросс-ревью по SOLID/чистоте кода и записать приёмку.

## Границы

Пакетное чтение envelopes, кэширование scoped references, изменение группировки
outbox и параллелизм ingress остаются кандидатами для отдельного обоснования
после первого изменения. Не объединять транзакции разных автоматов ради скорости,
не ослаблять проверки конфликтов и не менять хранилище Worker. Production SLA
не задан; tmpfs-профиль не измеряет задержки постоянного production-диска.
