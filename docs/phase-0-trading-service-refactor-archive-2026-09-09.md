# Веха 0 (цель 1): Рефакторинг сервиса торговли и ядра SOLID-изоляции

Документ описывает текущую итерацию (веха 0) для стабилизации архитектуры и
перехода к изолированной архитектуре `view -> usecase -> service -> repository/adapter`
без изменения предметной модели торговых алгоритмов.

Актуализация 2026-09-09: переход на единую baseline-схему и typed runtime
завершён, sandbox запущен. Исторические пункты ниже о переносе прежних таблиц
сохраняются как описание прежних этапов; текущая архитектура не импортирует
историю из старых хранилищ. Вехи 0.2, 0.3, 0.5, 0.7 и 0.8 приняты.
Остатки 0.1/0.6 закрыты, выполнен изолированный benchmark 0.9.3:
[результаты и границы проверки](milestone-0.9.3-acceptance-2026-09-09.md).

Критерий завершения каждой подзадачи: тест, подтверждающий DoD.
Исключение — фронт: для фронтенда критерий — контрактные/интеграционные проверки
и ручная приёмка. Функциональные UI-тесты не вводим в этой фазе.

Ключевое правило приёмки подзадачи: после каждого этапа выполняется **полная
регрессия** `pytest -q` (или эквивалент по релевантной плоскости). Любые падения
классифицируются:

- **Категория A — валидная регрессионная разница интерфейса/семантики**  
  падения из-за различий контрактов, интерфейсных изменений и изменившейся семантики.
  Они считаются ожидаемыми при эволюции и должны быть **исправлены в рамках текущей
  задачи** с соблюдением согласованности DoD.

- **Категория B — DoD-расхождения**  
  падения, где требуется переопределение условий тестов по DoD (не баг в реализации,
  а изменение критерия приемки/обозначения требований).
  Такие падения не исправляются сразу в рамках текущей задачи. Они фиксируются в плане
  как отдельная итерация с отдельной проверкой.

- **Категория C — дефекты реализации**  
  падения из-за ошибок в коде/реализации. Должны быть исправлены обязательно до
  закрытия подзадачи.

Этап считается закрытым только при нулевом числе падений категории C и при фиксации
всех падений категории B отдельным планом следующей итерации.

- `[~]` — выполняется, часть покрытий еще на доработке

## 0.3. Единый жизненный цикл и границы сервисов (CORE ↔ Worker) (CRIT)

- **Цель:** закрепить, что торговый сервис не является источником истины по позициям и
  статусам; core владеет authoritative view, worker — execution facts + audit-снимки цикла.
- **Статус:** [x]
- **Приёмка:** [763 теста, review и локальное развёртывание](milestone-0.3-acceptance-2026-09-09.md).

### 0.3.1. Явные состояния и переходы

1. Зафиксировать единый enum состояний и переходы: `IN_QUEUE`, `OPENING`,
   `IN_WORK`, `HOLD`, `CLOSED`; граф определяется общей политикой с учётом
   инициатора перехода. Bootstrap сохраняет `HOLD -> IN_WORK` через атомарную
   группу фактов, пользовательский resume — `HOLD -> IN_QUEUE`.
2. Вынести правила переходов в service/usecase слой worker и core.

## 0.4. Отдельный БД-сервис и контейнеризация хранилища (MAJOR)

- **Цель:** выделить БД как независимый сервисный слой с отдельными DSN/миграциями.
- **Статус:** [x] — `0.4.1–0.4.8` реализованы и приняты.
- **DoD:** local Docker Compose поднимает PostgreSQL как отдельный сервис;
  Core является единственным runtime-клиентом PostgreSQL, Worker использует
  собственную SQLite и не получает Core DSN.

### 0.4.1. Переход к отдельному сервису БД

- **Статус:** [x]

1. Compose-сервис PostgreSQL 16 имеет собственный healthcheck и внешний volume.
2. Alembic выполняется явным one-shot job `moex-migrate-schema`; Core startup не
   изменяет схему.
3. Core использует проверяемые pool settings и сообщает отдельно database/schema
   health.

### 0.4.2. Разделение подключений

- **Статус:** [x]

1. Только Core получает PostgreSQL `DATABASE_URL`.
2. Worker принимает только `AUTOMATON_DATABASE_URL=sqlite:///...` и хранит
   recovery в локальной БД.
3. PostgreSQL и внешний Worker volume имеют независимые lifecycle и backup
   responsibility.

### 0.4.3. Перенос legacy Core и runtime cutover

- **Статус:** [x]

1. Legacy SQLite переносится read-only командой
   `moex-migrate-core-database` с dry-run-by-default.
2. Apply выполняется restartable chunk-ами; повторный apply и независимый dry-run
   подтвердили точное совпадение данных.
3. Core переведён на PostgreSQL, а исходный SQLite volume сохранён для rollback.

### 0.4.4. Автономное recovery-хранилище Worker

- **Статус:** [x]

1. Существующий Worker volume объявлен внешним как
   `moex-sentinel_automaton-data`.
2. Пересоздание только Worker подтвердило сохранность cached commands, intents и
   outbox без PostgreSQL-доступа.

### 0.4.7. Эксплуатационная документация

- **Статус:** [x]

1. README, AGENT_BRIEF и development runbook описывают PostgreSQL setup, явную
   миграцию, перенос, backup/rollback и удалённый Worker.
2. Обычная эксплуатация явно запрещает удалять volumes через
   `docker compose down -v`.

### 0.4.8. Финальная приёмка и rollback rehearsal

- **Статус:** [x]

1. Пересобрать application images без удаления внешних volumes.
2. Повторить schema/transfer idempotency и end-to-end runtime checks.
3. Недеструктивно отрепетировать возврат Core на сохранённую legacy SQLite и
   последующее восстановление PostgreSQL runtime.

**DoD:** все runtime и regression gates пройдены; после этого `0.4` получает

## 0.5. Отдельный аналитический сервис (MAJOR)

- **Цель:** выделить единый источник рыночной аналитики (order book + candles + признаки),
  чтобы worker выполнял только принятие решения + execution.
- **Статус:** [x] Код, регрессия и кросс-ревью выполнены; после восстановления
  stream подтверждены новые решения Worker и доставка фактов. Непрерывная
  свежесть всех инструментов не подтверждена; stale изолируется по TTL.
  [Фактические результаты](milestone-0.5-acceptance-2026-09-09.md).
- **DoD:** аналитика/кадры стакана и свечей запрашиваются через внутренний контракт,
  decision path использует снапшот с `snapshot_id` и `freshness`.

### 0.5.1. Границы сервиса

1. Аналитический сервис получает только рыночные порталы, не знает о брокерских токенах,
   портфелях и статусах заявок.
2. Worker получает готовые метрики + свежесть, но не дергает рынок напрямую в основном цикле.

### 0.5.2. Контракт и кэш

1. Определить proto/json-contract для snapshot-ответа.
2. Добавить метаданные `captured_at`, `snapshot_id`, `ttl`.

### 0.5.3. Проверка

1. Сервисные тесты:
   - stale snapshot не допускает новых активных действий;
   - fresh snapshot позволяет full-cycle decision для N позиций за tick.

## 0.7. Единая динамическая стратегия (MAJOR)

- **Цель:** использовать один определённый кодом алгоритм для всех позиций,
  пересчитывать адаптивные пороги по рынку и сохранить существующий механизм
  проверки свободных средств и резервирования заявок.
- **Статус:** [x] Единая идентичность, динамический пересчёт и неизменность
  истории проверены; обновление развёрнуто в локальном Compose.
  [Приёмка и ограничения](milestone-0.7-acceptance-2026-09-09.md).
- **DoD:** единый алгоритм использует актуальные адаптивные значения Analytics;
  история решения сохраняет применённые параметры. Код и версия алгоритма
  согласованы между API и Worker; пересчёт и неизменность истории подтверждены
  сквозными тестами. Размер покупки и резервы сохраняют текущую семантику.

### 0.7.1. Domain contract strategy

1. Согласовать код и версию единственного алгоритма в Worker, API и новых
   диагностических фактах. Существующие исторические факты неизменяемы.
2. Убрать дубли определения общих параметров; отличать резервные значения
   от фактических адаптивных порогов каждого инструмента.
3. Стратегия определяется кодом: каталог шаблонов в БД, назначение стратегии
   позиции и миграции таких назначений не входят в архитектуру.

### 0.7.2. Настройки ресурсов и история решений

1. Использовать существующие общий размер покупки в лотах, доступные средства
   счёта и резервы активных заявок. Индивидуальных бюджетов позиции сейчас нет;
   по решению пользователя новые поля и настройки не вводятся.
2. Динамические пороги рассчитываются Analytics по завершённым свечам и
   используются Worker вместе со стаканом одного рыночного поколения.
3. `decision.strategy_snapshot` и `decision.indicators` — история входов
   конкретного решения, а не настраиваемая стратегия в БД. Новый расчёт
   не изменяет уже записанное решение и первоначальные факты его заявки.
4. Глобальное разрешение торговли, TTL и доставка фактов сохраняют отдельную
   операционную ответственность.

### 0.7.3. Тесты

1. Проверить единую стратегию MVP и разные адаптивные пороги инструментов
   при разных рыночных данных.
2. Проверить стабильность одного поколения, пересчёт на новых входных данных
   и переходы ADAPTIVE → FALLBACK → ADAPTIVE.
3. Проверить неизменность исторических решений и заявок после следующего
   расчёта и перезапуска, а также запрет новых intent по stale TTL.
4. Сохранить проверки свободных средств, восстановления резервов и запрета
   новых intent при `STRATEGY_ENABLED=false`; алгоритм исполнения сохраняется.
