# MOEX Sentinel — единый архитектурный документ

## 0) Назначение и уровень консолидации

Данный документ — рабочая основа MVP и единственная согласованная база описания архитектуры на текущий этап. Его цель — устранить противоречия между итерационными планами и зафиксировать фактические границы и договорённости между компонентами.

## 1) Область MVP

- Режимы: `TEST` и `PROD` в переключателе, но в текущей версии выполняется только интеграция с sandbox.
- MVP покрывает: брокеры, аккаунты, портфель/позиции/операции, торговые контуры, аналитический дашборд, контрактные API и наблюдаемость.
- Торговля и чтение данных выполняются через официальный `t-tech-investments` по sandbox endpoint `sandbox-invest-public-api.tbank.ru:443`.
- Конфигурация брокеров и подтверждённые торговые данные хранятся в Core PostgreSQL. Worker SQLite содержит только восстановимое состояние исполнения и typed outbox. Отдельный `portfolio-snapshot-worker` также относится к Core и сохраняет снимки непосредственно в PostgreSQL.
- Analytics — отдельный процесс без credentials и постоянного хранилища;
  он рассчитывает показатели по рыночным снимкам Core. Актуальная
  [карта владения данными](data-ownership.md) связывает таблицы с проверками целостности.

## 2) Единая постановка фактов (trade-facts) и границы данных

На каждом цикле обработки автомат фиксируется последовательность фактов с временной меткой:

- решение (decision) по автомату;
- создание/изменение жизненного цикла intent;
- фактическое состояние заявки (dispatch/reconcile/result);
- бизнес-аудит шага принятия решения.

### 2.1 Поставка данных в БД

- Для `Core` сохраняются доменные агрегаты и статусы автоматов.
- Для `trading_automaton` сохраняются durable факты исполнения и бизнес-аудит.
- Все записи для воспроизведения алгоритма должны содержать `occurred_at`, а для audit-событий `process_id` + `event_id`.
- Единственный runtime-протокол использует `/internal/automation-commands`, `/internal/automation-statuses` и `/internal/automation-facts`. Core принимает группу фактов автомата в одной транзакции; повтор распознаётся по UUID события и последовательности `(automation_id, sequence_number)`.

### 2.2 Поток между сервисами (текущая постановка)

`Core view -> usecase -> service -> storage/ports -> repository`

`Worker runtime -> usecase -> service/domain -> repository -> local SQLite/outbox -> Core`

Конечные операции и владельцы ресурсов:

| Вход | Прикладная операция | Что остаётся вне юзкейса |
| --- | --- | --- |
| Core internal market HTTP | `GetMarketSnapshotUsecase` | Gateway владеет рыночными подписками и кэшем |
| Core readiness HTTP | `CheckReadinessUsecase` | Composition внедряет проверки БД и схемы |
| Core catalog sync | `SynchronizeBrokerInstrumentsUsecase` | Общий `ConfiguredPositionAdoptionService` вызывается после синхронизации; вложенного юзкейса нет |
| Portfolio worker tick | `CollectPortfolioSnapshotsUsecase` | Цикл/остановка в worker; короткие Session и run lock в storage adapter; расчёты счетов в collection service |
| Analytics HTTP | `CalculateAnalyticsSnapshotUsecase` | HTTP client принадлежит lifespan; расчёт показателей выполняется без I/O |
| Worker startup | `RecoverWorkerRunUsecase` | Signal handling, finish-run marker и закрытие ресурсов остаются в CLI |
| Worker control iteration | `SynchronizeTradingRuntimeUsecase` | Coordinator владеет broker tasks/bundles и heartbeat |
| Worker broker iteration | `RunBrokerIterationUsecase` | Runtime владеет периодичностью, retry delay, lock и остановкой |

У каждого изменяемого runtime-состояния один владелец: команды и обработанные
поколения находятся в broker usecase, event остановки и блокировка — в broker
runtime. Замена команд во время I/O видна повторной проверке перед решением.
Остановка ждёт выполняемую итерацию перед закрытием SDK/client. Подготовка
восстановления выполняется и при недоступной Analytics.

Хранилище Worker применяет чистые domain-переходы торгового цикла в той же
транзакции, что intent, исполнение, лоты и outbox. Оно не создаёт бизнес-сервис.
Сборщик портфеля удерживает отдельный run lock во время чтения счетов, но не
держит data Session через broker awaits; окончательная запись run и снимков
атомарна. Для SQLite она явно открывает физическую транзакцию перед SAVEPOINT.

- Core не выполняет решение по рынку напрямую.
- Core поддерживает рыночный поток и историю, Analytics рассчитывает показатели
  одного поколения, Worker принимает торговое решение по этому снимку.
- Брокерский слой и storage строго инкапсулируются в соответствующем модуле.

## 3) Контракты данных и API

### 3.1 Pydantic как единый формат передачи

С конца этого этапа все внешние и межкомпонентные DTO должны быть Pydantic-моделями (`BaseModel`):

- `views/schemas/*`
- `sentinel_contracts/*`
- `domain` и сервисные входы/выходы там, где это часть интерфейса компонентов

Внутренние ORM-модели остаются SQLAlchemy-моделями. Внешние и межкомпонентные DTO,
включая неизменяемый `BootstrapResult`, описаны Pydantic-моделями.

### 3.2 Контракт OpenAPI

- Генерация файлового контракта должна быть повторяемой.
- Актуальный контракт хранится в `docs/contracts/openapi.yaml` и обновляется при изменения API.
- Генерация выполняется из приложения FastAPI (`create_app`).
- Любые изменения контрактов API должны сопровождаться обновлением этого файла и короткой проверкой ссылок/валидности.

### 3.3 Проверка целостности T-Invest SDK

- SDK должен быть доступен только по утвержденной версии и через sandbox target.
- В адаптерах проверяется, что неподдерживаемые окружения отклоняются.
- Контрактные тесты должны валидировать не только сигнатуру методов в SDK, но и корректное покрытие наших usecase-границ: catalog/market/portfolio/operations/order/market_data.

## 4) Поведение статусов и бизнес-сценарии

Фактический алгоритм принятия торговых решений и известные расхождения runtime
зафиксированы в [нормативной спецификации стратегии](trading-strategy.md).

- `IN_QUEUE`: заявка создана, ждёт обработки воркером.
- `IN_WORK`: в обработке/исполнении.
- `HOLD`: приоритетный стоп по рискам/ошибке/политике; ручное возобновление только через `RESUME`.
- `CLOSED`: автомат закрыт после терминализации всех активных intent.

Согласованный жизненный цикл:

1. Core меняет статус на `IN_QUEUE`;
2. runtime берёт batch, читает статус/версию, делает decision;
3. фиксирует intent и событие в local durable storage;
4. отправляет брокеру (или реконcилиирует);
5. пишет результат в Core через fact-provider с фактическими статусами и audit.

## 5) Наблюдаемость

- process_id на уровне шага бизнес-логики.
- аудит решения (`TRACE`/`INFO`/`WARN`/`ERROR`) через контрактную модель audit-события.
- минимальные SLA-логи должны сохраняться в БД (не только в stdout).

## 6) Data model: время и порядок событий

- Любой бизнес-записанный факт должен иметь явную метку времени факта (`occurred_at`), для случаев восстановления состояния — отдельный `created_at`/`updated_at` по возможности.
- Для записей о последовательностях (`sequence_number`, `revision`) время обязано быть синхронизировано с событием, чтобы воспроизвести историю шагов в любом состоянии.
- Persisted-время нормализуется до UTC с точностью до миллисекунд. Время не заменяет устойчивые идентификаторы событий и `sequence_number`.
- Core использует одну Alembic-цепочку `0001_baseline` → `0002_portfolio_snapshot_runs`. Приложение само схему не меняет; миграции запускаются отдельной командой. История из старых хранилищ не импортируется. Forward migration снимков не изменяет торговые таблицы и требует пустой старой таблицы снимков.

## 7) Завершённый baseline и актуальный план

Текущая очередь работ находится в [актуальном плане](phase-1-implementation-plan.md).
Clean-slate runtime и сводка торговли уже реализованы. Фактическая открытая позиция
принимается как HOLD/BOOTSTRAPPING; после подготовки Worker создаёт начальные
cycle/lot с нулевой историей комиссий и realized P&L. Четыре typed факта
принимаются атомарно, последним идёт IN_WORK. Bootstrap не создаёт брокерскую
заявку или исполнение.

Сводка `/api/trading/summary` читает только сохранённые снимки Core, агрегирует
валюты отдельно и возвращает фактические границы периодов. Сам HTTP-запрос
к брокеру не обращается. Порядок безопасного обновления и операционные проверки
описаны в [runbook](clean-slate-cutover.md).

## 8) Тестовая стратегия после консолидации

### 8.1 Документационные тесты

- `tests/test_documentation.py` проверяет только актуальные документы.
- Итерационные материалы не должны оставаться как обязательные источники истины.

### 8.2 Контракты и адаптеры

- `tests/adapters/test_tinvest_sdk_contract.py`: целостность версии SDK, sandbox target и минимального набора методов.
- `tests/test_contracts.py`/`tests/adapters/*` — проверка соответствия `sentinel_contracts` и API-схем.

### 8.3 Поведенческие тесты

- Usecase/service tests остаются источником регрессионного поведения.
- Тестовая стратегия не расширяется в глубину структуры файлов; проверяется контракт и эффект.
