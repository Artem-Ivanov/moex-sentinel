# Веха 0: завершённый архитектурный baseline

Актуализировано 2026-09-10 по кодовой базе и уточнениям пользователя.
Вехи 0.1–0.8 завершены. Текущая очередь работы находится в
[актуальном плане](phase-1-implementation-plan.md); повторно выполнять закрытые
этапы не требуется. Статусы ниже опираются на датированные приёмки, а не на новый
запуск тестов или новую проверку работающего Compose.

[Пунктовая сверка прежних требований](milestone-audit-2026-09-09.md) объясняет
каждое сохранение, уточнение и исключение. [Прежний план](phase-0-trading-service-refactor-archive-2026-09-09.md)
сохранён как архив; его команды, shadow-схемы и промежуточные gates не действуют.

## 0.1. Pydantic-владение и ликвидация `@dataclass` (CRIT)

**[x] Завершена.** Контрактные DTO используют Pydantic; ORM остаётся SQLAlchemy,
объекты жизненного цикла — обычными классами. Последний `BootstrapResult`
переведён на frozen Pydantic DTO. Декораторов `@dataclass` в `src` нет;
`@dataclass_transform` — отдельная аннотация типизации.

Доказательства: [bootstrap DTO](../src/trading_automaton/services/position_bootstrap.py),
[тесты bootstrap](../tests/trading_automaton/services/test_position_bootstrap_service.py),
[закрытие остатка 0.1](milestone-0.9.3-acceptance-2026-09-09.md).

## 0.2. Реструктурирование структуры БД и единых фактов (CRIT)

**[x] Завершена.** Core PostgreSQL принимает один typed поток фактов от Worker
SQLite. UUID, sequence и revision обеспечивают идентичность, порядок и контроль
состояния; группа автомата принимается атомарно. Repository проверяет общую
связь инструмента, автомата и цикла поверх scoped FK. UTC хранится с точностью
до миллисекунд. Локальное восстановимое состояние Worker и подтверждённая
проекция Core имеют разных владельцев; это предусмотренная архитектура.

Текущая цепочка: `0001_baseline` → `0002_portfolio_snapshot_runs`. Импорт старой
истории и shadow cutover заменены clean-slate запуском. Повторяемые WAIT остаются
аудируемыми решениями; подавление всего такого аудита не требуется.

Доказательства: [владельцы таблиц и тесты](data-ownership.md),
[приёмка 0.2](milestone-0.2-acceptance-2026-09-09.md),
[ограничения PostgreSQL](../tests/integration/postgresql/test_schema_constraints.py).

## 0.3. Единый жизненный цикл и границы сервисов (CORE ↔ Worker) (CRIT)

**[x] Завершена.** Общая политика различает команды пользователя и предложения
Worker. Core подтверждает состояние; CLOSED терминален. Bootstrap переводит
HOLD/BOOTSTRAPPING в IN_WORK последним фактом атомарной группы. Обычный resume
выполняется командой Core. Этапы решения и исполнения связаны `process_id`.

Доказательства: [политика](../src/sentinel_contracts/automation_lifecycle.py),
[интеграция двух сервисов](../tests/integration/test_core_worker_lifecycle.py),
[приёмка 0.3](milestone-0.3-acceptance-2026-09-09.md).

## 0.4. Отдельный БД-сервис и контейнеризация хранилища (MAJOR)

**[x] Завершена в текущей архитектуре.** PostgreSQL — отдельный Compose-сервис;
Core HTTP backend и portfolio snapshot worker используют его в одной границе
владения. Схему обновляет отдельный migration job. Worker получает только свой
SQLite URL. Оба persistent volume сохраняются при обновлении приложений.

Перенос прежней Core SQLite и возврат runtime на неё исключены из действующих
процедур после clean-slate решения. Старые volumes нельзя удалять без отдельного
разрешения. Тесты БД выполняются на отдельном экземпляре.

Доказательства: [Compose](../compose.yml), [проверки Worker SQLite](../tests/trading_automaton/storage/test_worker_database.py),
[эксплуатация](development.md), [приёмка baseline](milestone-acceptance-2026-09-08.md).

## 0.5. Отдельный аналитический сервис (MAJOR)

**[x] Завершена.** Core владеет SDK stream и историей; отдельный Analytics без
credentials и persistence рассчитывает market-only batch. Worker использует
показатели и стакан одного поколения, проверяя TTL также перед отправкой заявки.
Непригодные данные одного инструмента исключаются отдельно. Детали инструмента
обновляют окно завершённых минутных свечей за последние два часа.

Доказательства: [Core gateway](../src/moex_sentinel/services/market_snapshot_gateway.py),
[Analytics](../src/market_analytics/service.py),
[сквозной контракт](../tests/integration/test_analytics_worker_contract.py),
[приёмка 0.5](milestone-0.5-acceptance-2026-09-09.md).
Непрерывная свежесть всех инструментов не заявлена; обработка отказа выделена в 0.9.5.

## 0.6. Страница брокеров и управления интеграциями (MAJOR)

**[x] Завершена.** `/brokers` отображает кодовый список адаптеров и управляет
пользовательскими подключениями; поддержаны форма, ошибки, счета и мобильный
экран. Backend владеет бизнес-валидацией, frontend обеспечивает ввод и показывает
ошибки контракта. Добавление реализации адаптера не происходит через UI.

Доказательства: [UI](../frontend/src/views/BrokersView.vue),
[API contract клиента](../frontend/src/api/brokers.ts),
[браузерный smoke](../develop/scripts/check_brokers_ui.mjs),
[приёмка UI](milestone-0.9.3-acceptance-2026-09-09.md#ui-и-регрессия).
Изменяющие сценарии выполнены с mock API; рабочий UI проверен GET/HEAD.

## 0.7. Единая динамическая стратегия (MAJOR)

**[x] Завершена.** Один кодовый алгоритм для всех позиций. Analytics пересчитывает
адаптивные пороги по завершённым свечам; общие параметры окружения служат fallback.
Код и версия согласованы между API и Worker. `strategy_snapshot` и `indicators`
сохраняют входы конкретного решения и не изменяются следующими расчётами.

Каталога и назначения стратегий в БД нет. Используются общий размер покупки,
доступные средства и резервы активных intent. По решению пользователя новые поля
индивидуального бюджета не вводятся. Ресурсы и рыночные пороги — разные понятия.

Доказательства: [идентичность](../src/sentinel_contracts/strategy.py),
[адаптация](../src/market_analytics/volatility_strategy.py),
[сквозные тесты](../tests/integration/test_dynamic_strategy_contract.py),
[приёмка 0.7](milestone-0.7-acceptance-2026-09-09.md).

## 0.8. Реструктурирование механики принятия решений (CRIT)

**[x] Завершена.** Покупка требует непрерывного SMA20 и подтверждённого разворота.
Выход учитывает комиссии и заданную семантику stop-loss. Исполнение, цикл и outbox
сохраняются атомарно; устаревшее наблюдение не создаёт новый intent после исполнения.
Повторяемый WAIT допустим, повторная отправка уже исполненной заявки — нет.

Доказательства: [спецификация стратегии](trading-strategy.md),
[матрица решений](../tests/trading_automaton/services/test_strategy_selection_matrix.py),
[execution graph](../tests/integration/test_execution_cycle_core_contract.py),
[приёмка 0.8](milestone-0.8-acceptance-2026-09-09.md).
