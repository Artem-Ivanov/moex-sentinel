# Веха 0.9.7: одно чтение идентичности входящего факта

Объём согласован пользователем 2026-09-10 после завершения 0.9.6.

## Основание и объём

В профиле 0.9.6 Core выполняет 102/103/106 SQL-запросов на WAIT-решение
при 6/20/50 инструментах. В `TradingFactIngressService` каждый факт требует
двух чтений принятого envelope: по event_id и по automation_id/sequence_number.

Объединить эти чтения в одну операцию `TradingAuditPort.find_envelope_matches`.
Репозиторий возвращает все строки, удовлетворяющие условию
`scope AND (event_id OR (automation_id AND sequence_number))`.
Первичный ключ события и уникальность scoped sequence ограничивают результат
двумя строками. Порядок результата не определён.

На прежнем WAIT-профиле ожидается экономия одного запроса на факт: девяти
на решение, то есть 93/94/97 SQL-запросов. Фактические count и latency должны
быть подтверждены повторным профилем; заранее ускорение не заявляется.

## Контракты

- Event совпадение имеет приоритет. Точный replay сравнивает весь envelope,
  кроме received_at, подтверждается без повторного mapper/append/CAS.
- Event другого автомата своего scope остаётся видимым. Чужой scope невидим
  для обеих веток; sequence проверяется только для входящего автомата.
- Event и sequence могут совпасть с двумя разными строками; обе должны попасть
  в результат, а конфликт event должен сохранить приоритет.
- Новые факты обрабатываются последовательно с видимостью предыдущих записей
  в той же транзакции. Ошибка откатывает целиком группу автомата; успешные
  соседние группы сохраняются.
- Ограничения БД и CAS остаются окончательной защитой от конкурентной записи
  после предварительного чтения. Семантика ошибок записи сохраняется.
- HTTP/Worker-протокол, схема БД, UTC/DTO и условия профиля сохраняются.

Пакетное предварительное чтение, кеши scoped references, группировка outbox,
параллелизм и перенос Worker storage требуют отдельного объёма.

## Приёмка

1. Матрица lookup на SQLite и отдельном мигрированном PostgreSQL: 0/1/2 строки,
   обе идентичности, границы scope/automation, полный payload и время;
   строго один SQL-запрос на lookup.
2. Production ingress: точный повтор без записей, внутригрупповой duplicate,
   event/sequence conflict, старый replay вместе с новым фактом, rollback и
   успешная соседняя группа.
3. Конкурентная доставка с двумя транзакциями PostgreSQL: одна фиксация,
   отсутствие payload проигравшего, повтор победителя и исправленная доставка.
4. Полная регрессия с PostgreSQL без пропуска PostgreSQL-наборов; Ruff/Black
   для затронутых файлов.
5. Прежний профиль 6/20/50, warmup=3, iterations=100, batch=100; отдельные
   результаты WAIT, начальных исполнений и восстановления после потери ACK.
   Новые JSON сохраняются рядом с историческими, а не заменяют их.
6. Независимое кросс-ревью кода и итоговой интеграции по AGENTS.md; обновление
   актуального индекса и приёмки с ограничениями измерений.
