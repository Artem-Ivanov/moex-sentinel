# Завершённая веха: 0.9.3 — устойчивость и производительность

UI брокеров. Benchmark на 6/20/50 инструментах выявил и помог исправить расход
лимита заявок на WAIT. Измерены цикл и доставка, подтверждено восстановление
после потери ACK. Worker и frontend обновлены в Compose.
[Результаты, кросс-ревью и ограничения](milestone-0.9.3-acceptance-2026-09-09.md).

Следующая запланированная веха —
[0.9.5: обработка недоступности песочницы](milestone-0.9.5-sandbox-resilience.md).
При десятиминутном наблюдении зарегистрированы UNAVAILABLE и примерно минутное
окно без свежих снимков. Возможен внешний отказ песочницы; по уточнению
пользователя устанавливать его причину для приёмки не требуется. Веха проверит
безопасное ожидание и восстановление приложения изолированными сценариями.
Перед оптимизациями доставки нужен отдельный профиль Core PostgreSQL:
изолированный benchmark использует SQLite и не подтверждает production SLA.

## Завершённая веха: clean-slate runtime

Статус на 2026-09-08: кодовая часть и запуск нового локального Compose-окружения
завершены. [Результаты приёмки](milestone-acceptance-2026-09-08.md) содержат
проверки, исправления и границы операционной проверки.

Операционный запуск подтверждён 2026-09-09: sandbox-подключение настроено
скриптом из `develop/`, каталог синхронизирован, пять автоматов завершили
bootstrap и перешли в IN_WORK. Снимок портфеля публикуется без ошибок.
При настройке исправлен доступ к чтению счетов у подключения DRAFT;
интеграционная регрессия проверяет переход DRAFT -> ACTIVE.

Цель вехи — запустить Worker с фактическими открытыми позициями брокера и продолжить торговлю через единый typed flow.

Реализуемый результат:

1. одна цепочка Core-миграций от `0001_baseline` до текущего `0002_portfolio_snapshot_runs` на пустой PostgreSQL;
2. настройка broker connection и `account_id` обычным UI/API;
3. синхронизация каталога и автоматическое создание HOLD/BOOTSTRAPPING для положительных позиций без активных заявок;
4. атомарное создание Worker cycle/lot и доставка полного набора bootstrap-фактов;
5. переход в IN_WORK только последним подтверждённым фактом;
6. обычные runtime-решения после bootstrap;
7. старые volumes остаются отсоединённым backup до отдельного разрешения на удаление;
8. отдельный процесс снимков портфеля и сохранённая сводка торговли по валютам;
9. forward migration существующей baseline-БД без смены volume и потери торговых данных.

Операционный чек-лист находится в [clean-slate-cutover.md](clean-slate-cutover.md).

Ход завершающей проверки: [план закрытия](superpowers/plans/2026-09-08-milestone-closeout.md).
