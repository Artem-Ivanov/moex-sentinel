# Шаблоны агентов MOEX Sentinel

Восемь редактируемых профилей: архитектор, независимый reviewer, security-аудитор,
два senior, два профильных junior и универсальный worker. Backend и frontend
разделены по границам проекта.
Root всегда оркестратор: поручает задачи, одобряет декомпозицию и принимает
пакет после независимого ревью. Реализацию поручает исполнителям.
Шаблоны хранятся в `.agents/` по решению владельца, рядом с проектными skills.
Это заготовки для правки; активная конфигурация Codex не изменена.

Формат — отдельный TOML с `name`, `description`, `developer_instructions` и
настройками модели. Codex обнаруживает проектные профили в `.codex/agents/`.
Проверено по [официальной документации OpenAI](https://learn.chatgpt.com/docs/agent-configuration/subagents)
и локальному `codex-cli 0.160.0`; фактический запуск этих профилей ещё не выполнен. Native discovery не активирован:
профили доступны для ручного назначения инструкций, модели и scope агенту.
Копирование в `.codex/agents/` и изменение конфигурации не входят в эту правку.

## Роли и настройки для начала

| Профиль | Задача | Модель / reasoning | Sandbox по умолчанию |
| --- | --- | --- | --- |
| [moex_architect.toml](moex_architect.toml) | Реальный поток, границы, контракт, пакеты и приёмка | `gpt-6.1-sol` / `high` | `read-only` |
| [moex_reviewer.toml](moex_reviewer.toml) | Независимая проверка плана, diff и доказательств | `gpt-6.1-sol` / `high` | `read-only` |
| [moex_security_auditor.toml](moex_security_auditor.toml) | Назначенный read-only аудит auth/authz, сессий, CSRF, секретов и trust boundaries | `gpt-6.1-sol` / `high` | `read-only` |
| [moex_backend_developer.toml](moex_backend_developer.toml) | Senior: сложная спроектированная backend/financial/security работа и интеграция junior | `gpt-6-luna` / `high` | `workspace-write` |
| [moex_frontend_developer.toml](moex_frontend_developer.toml) | Senior: спроектированный frontend/API поток и интеграция junior | `gpt-6-luna` / `high` | `workspace-write` |
| [moex_junior_backend_developer.toml](moex_junior_backend_developer.toml) | Маленькая независимая backend часть по одобренному brief | `gpt-6-luna` / `low` | `workspace-write` |
| [moex_junior_frontend_developer.toml](moex_junior_frontend_developer.toml) | Маленькая независимая frontend часть по одобренному brief | `gpt-6-luna` / `low` | `workspace-write` |
| [moex_worker.toml](moex_worker.toml) | Универсальные ограниченные leaf-задачи реализации, тестов, рефакторинга и документации | `gpt-6-luna` / `low` | `workspace-write` |

Модель — стартовое предложение, доступность зависит от аккаунта. TOML принимает
одно значение `model_reasoning_effort`: root может назначить `medium` для большего,
но ясно ограниченного junior/worker leaf-пакета и `xhigh` для сложной архитектуры
или auth/security review. Это решение указывается в брифе запуска, а не как
массив или диапазон TOML. Senior backend/frontend остаются на `high`.
Цена и скорость этих профилей не измерены; настройка не гарантирует экономию,
скорость или качество.
Модель основного координатора задаётся отдельно в клиенте.

`sandbox_mode` задаёт настройку профиля, а не отдельную систему полномочий.
Унаследованные ограничения и текущие runtime overrides основного сеанса могут
иметь приоритет. Профиль не выдаёт доступа к VPS, брокеру или рабочей БД.
[Правила наследования](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls).

## На каких документах основаны инструкции

- [AGENTS.md](../AGENTS.md): независимое кросс-ревью, сохранность изменений,
  отдельный тестовый экземпляр БД, рабочие материалы и журналирование.
- [AGENT_BRIEF.md](../AGENT_BRIEF.md): постоянные контракты и финансовые инварианты.
- [Очередь](../docs/phase-1-implementation-plan.md): актуальные вехи и незавершённое.
- [Оркестрация и Worker storage](../docs/audits/orchestration-and-worker-storage.md):
  Worker управляет исполнением; его SQLite/outbox — durable состояние, а не кеш.
- [README](../README.md), [pyproject](../pyproject.toml),
  [frontend/package.json](../frontend/package.json): стек и команды проверки.
- `develop/CURRENT.md`: локальная точка продолжения, если существует; не источник
  постоянных правил и не подтверждение свежего состояния сервера.

Шаблоны не копируют всю очередь и старые разрешения. Источники требований
нужно перечитывать по назначенной задаче. Навыки загружаются из доступного
каталога skills по необходимости; абсолютные пути к пользовательским plugins
не зашиты в TOML. В другом окружении нужные skills должны быть установлены.

## Что редактировать

1. `model` и `model_reasoning_effort` — модель и глубину для роли.
2. `description` — условия, при которых координатор назначает роль.
3. `developer_instructions` — обязанности, границы и формат результата.
4. Границы senior/junior — назначайте независимые пакеты и точные списки файлов;
   маленькая часть идёт junior, сложная остаётся senior.

Постоянные общие правила меняйте в AGENTS/AGENT_BRIEF и сверяйте с шаблонами.
Право менять файл задаётся конкретным заданием. Каталог backend или frontend
не означает разрешения переписать всю его область.

## Рабочий порядок

```text
root (оркестратор)
  ├─ архитектор → план и контракты → root
  ├─ senior backend → одобренные root части → junior backend
  ├─ senior frontend → одобренные root части → junior frontend
  ├─ junior backend/frontend или worker ← однопунктовый brief напрямую от root
  ├─ security auditor ← явно назначенный read-only аудит → root
  └─ независимый reviewer ← пакет и итоговая интеграция от root
junior → diff/доказательства → parent senior/root → review/integration → root
```

1. Root сверяет контекст и поручает задачу исполнителю. Архитектор исследует
   поток и контракт, когда это требуется; reviewer проверяет план при изменении
   границ, схем или финансового поведения.
2. Каждый senior обязательно декомпозирует задачу до реализации: для маленькой
   хватит одного пункта. Root явно одобряет границы, точные файлы/владельцев,
   цель/контракт, риски, зависимости, модель/reasoning и приёмку до реализации
   и передачи junior. Это внутренний ACK агентов; повторное разрешение человека на авторизованную работу не нужно.
3. Маленькие независимые части с понятным контрактом senior передаёт junior.
   Сложная работа, финансовая логика, auth/security, миграции БД, идемпотентность
   и outbox/recovery остаются senior. Root может напрямую поручить маленькую
   независимую часть junior с однопунктовым brief; parent тогда root.
   Общий API/тип/схему изменяет один назначенный владелец.
4. Senior запускает только junior по одобренному root brief и при свободном
   лимите сеанса. Иначе запрашивает root запуск или последовательное исполнение;
   лимит не обходится. Архитектор и reviewer не запускают агентов самостоятельно.
   Junior и worker — leaf: не запускают агентов, не расширяют scope, эскалируют сложность
   senior/root, не переключает модель/reasoning без ACK root и не принимает
   собственный пакет.
5. Junior возвращает diff и проверки parent senior/root. Senior отвечает за review,
   достаточные проверки и интеграцию его работы, затем передаёт единый пакет root.
6. Независимый reviewer, не участвовавший в реализации, проверяет актуальный diff
   и итоговую интеграцию. Critical/Important исправляются и независимо
   перепроверяются до принятия; senior review не заменяет эту проверку.
7. Root поручает достаточные интеграционные проверки, собирает доказательства,
   принимает пакет и один обновляет общий CURRENT/WORK_LOG и очередь. Исполнители
   возвращают ему текст результата, чтобы избежать гонок.
8. Владелец коммитит; деплой следует после его отмашки. Реальная торговля требует
   отдельного допуска. Ни одна из ролей самостоятельно не выполняет
   stage/commit/push/deploy или операции с рабочими данными.

Тесты с временными файлами, cache и отдельной тестовой БД выполняют назначенные
разработчики. Read-only reviewer проверяет доказательства и передаёт недостающие
команды root для назначения запуска; это не собственный запуск тестов reviewer.
Восемь профилей не требуют восьми одновременно работающих агентов. Свободные
слоты считаются по фактическому лимиту сеанса, включая root и живых исполнителей.
Новые профили не повышают лимит и не разрешают live API/SSH, торговлю или удаление
истории, recovery journals и persistent volumes.

## Подключение после правки

Из корня репозитория скопируйте отредактированные профили:

```bash
mkdir -p .codex/agents
cp -n .agents/moex_*.toml .codex/agents/
```

`cp -n` сохраняет уже существующие профили: для их обновления сравните и замените
нужные файлы вручную. После копирования источником для запуска являются файлы
в `.codex/agents/`; последующая правка `.agents/` сама их не обновляет.

При необходимости добавьте в проектный `.codex/config.toml` эту секцию,
сохранив остальные настройки и объединив её с существующей `[agents]`:

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 3
```

Это максимум трёх открытых саб-агентов без учёта основного координатора.
Опция и её legacy alias описаны в
[Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference).
Ограничение текущего клиента/сеанса может быть ниже.
Откройте новый сеанс Codex в доверенном проекте и запросите задачу по именам ролей.
Клиент должен обнаружить профили; это отдельная проверка подключения после
редактирования, а фактическое число слотов определяется текущим runtime.

## Шаблон задания координатора

```text
Роль: moex_architect / moex_reviewer / moex_security_auditor /
      moex_backend_developer / moex_frontend_developer /
      moex_junior_backend_developer / moex_junior_frontend_developer / moex_worker
Parent senior/root (для junior):
Модель/reasoning и доступный лимит сеанса:
Цель и критерии приёмки:
Источники требований (конкретные документы/разделы):
Текущее состояние и уже разрешённые действия:
Контракт входа/выхода и затронутые потребители:
Декомпозиция senior (даже один пункт для маленькой задачи):
Границы каждой части, точные файлы и единственный владелец каждого:
ACK root на границы/владельцев/модель/приёмку до реализации и junior brief:
Цель/контракт, риски и зависимости каждой части:
Маршрут junior: senior после ACK root либо direct root с однопунктовым brief;
                разрешённые файлы, parent senior/root, условия эскалации:
Чужие изменения, которые нужно сохранить:
Окружение проверки (отдельная тестовая БД, без рабочей БД/реальных заявок):
Команды/доказательства, которые нужно вернуть:
Ограничения и незавершённое:
```

Для ревью добавьте список новых файлов и актуальный diff/commit, требования,
результаты проверок и авторов. Не ограничивайтесь одним диапазоном коммитов,
если изменения ещё не закоммичены. Не передавайте секреты в бриф или отчёт.
