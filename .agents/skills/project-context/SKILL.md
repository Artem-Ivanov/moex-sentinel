# Контекст проекта MOEX Sentinel

Загружай сведения по задаче, а не весь архив проекта. `AGENTS.md` задаёт
обязательные правила; локальный `develop/CURRENT.md`, если есть, передаёт текущий статус;
`develop/WORK_LOG.md` хранит локальную историю и может отсутствовать в другом
checkout. Скилл не заменяет правила `AGENTS.md`.

1. В начале работы прочитай `develop/CURRENT.md`, если он есть, и проверь `git status --short`.
   В новом checkout прочитай `README.md`, `AGENT_BRIEF.md` и нужные разделы очереди;
   создай локальный CURRENT из `develop/CURRENT.example.md`, не заменяя существующий
   файл и не записывая неизвестный runtime как подтверждённый.
   Сверь нужные файлы и состояние сервисов перед выводом о текущем положении.
   Старые отчёты подтверждают только состояние на дату их проверки.
2. Выбери подробности по теме: очередь и вехи —
   `docs/phase-1-implementation-plan.md`; границы сервисов — `AGENT_BRIEF.md`;
   конкретная веха — её постановка и связанные доказательства из `CURRENT.md`.
   Для истории, если локальный `WORK_LOG.md` есть, сначала найди нужный
   заголовок, затем прочитай только соответствующую запись. Если пользователь
   просит лишь указать место доказательств, дай ссылки из `CURRENT.md` или
   тематического документа; содержимое отчётов читай при запросе проверки.
   Не загружай весь журнал по умолчанию.
3. После значимого результата или перед завершением обнови короткий `CURRENT.md`:
   подтверждённое состояние, следующий конкретный шаг, блокировки и ссылки на
   доказательства. Подробный ход и результат допиши в локальный `WORK_LOG.md`;
   важные решения внеси в отслеживаемый тематический документ. Не переноси
   длинные логи, секреты или устаревшие промежуточные статусы в `CURRENT.md`.

Если `CURRENT.md` расходится с актуальным checkout или проверкой runtime,
исправь его по подтверждённым данным; неизвестное состояние назови неизвестным.
Кросс-ревью изменений выполняй по `AGENTS.md`.
